# Анализ перфоманса: игра-в-панели (Game.Sandbox)

_Автономное расследование 2026-06-23. Машина: Quadro RTX 4000, present=Mailbox, MSAA off, аналитическое AA вкл._
_Метод: реальные прогоны Game.Sandbox + лог `App FPS` + временный per-service Stopwatch + A/B-тумблеры (откатаны)._

## TL;DR

**Деградация — НЕ из sync-слоя.** Шина синхронизации (timeline-семафоры produce/consume + копия resolve→shared) стоит **≈0**: её отключение не меняет FPS. Реальная цена — **полный 3D-рендер игры, который выполняется КАЖДЫЙ UI-кадр, серийно с UI на ОДНОЙ GPU-очереди**.

## Замеры

| Сценарий | App FPS | мс/кадр | per-service (Stopwatch) |
|---|---|---|---|
| **UI без игры** (рендер игры пропущен) | **~375** | ~2.67 | WindowRenderService ~2.1 мс |
| **UI + игра-в-панели** | **~155** | ~6.45 | RenderingService ~3.3 мс + WindowRenderService ~5.7 мс |
| UI + игра, **sync отключён** (нет produce-wait/consume-signal + нет копии) | **~153** | — | ≈ как baseline |

(Первый «холодный» прогон давал ~485 — игра-в-панели ещё не начала рендер; согласуется с «UI без игры».)

## Что это значит

1. **Sync-семафоры/копия ≈ 0 цены.** A/B (`ADAMANTIUM_NO_GAMESYNC`) не дал разницы (153 vs 156). Игра и UI и так на ОДНОЙ `GraphicsQueue` и в ОДНОМ серийном цикле (`EntityServiceManager.Draw`: для каждого рендер-сервиса `BeginDraw→Draw→EndDraw→Submit`), поэтому GPU их уже сериализует сам — семафоры лишь упорядочивают, бесплатно.
2. **Главная цена — 3D-рендер игры (~3.3 мс), каждый UI-кадр.** `Adamantium.Engine.RenderingService` рендерит полную сцену (F-15) без ограничения частоты — на каждый тик `ApplicationLoopThread`.
3. **UI-сервис «толстеет» 2.1→5.7 мс с игрой** не потому, что UI стал тяжелее, а потому что его `BeginDraw` (ожидание fence) поглощает GPU-время игры на общей очереди — сериализация всплывает как CPU-ожидание в слоте UI. Суммарный GPU/кадр ≈ game(3D) + UI + composite ≈ 6.4 мс серийно.
4. **Не виноваты:** present (Mailbox, не vsync — FPS не закэплен рефрешем); frames-in-flight (`BuffersCount=3` — конвейер CPU↔GPU есть); аналитическое AA (UI с включённым AA = 375 FPS, MSAA-off это компенсирует). Аппликация и так настроена `DesiredFPS=300` (`Sandbox/Program.cs:13`) — 1000 не цель в принципе, а 155 < 300 ⇒ упор в рендер ниже капа.

## Где вернуть перф (по убыванию выгоды)

1. **[КРУПНО] Развязать частоту рендера игры от UI.** Сейчас игра перерисовывается 155×/сек, хотя панели хватит 60. Если рендер-сервис игры (или `GameOutput`) пропускает `Draw`/`CopyOutput`, пока не истёк его таргет-интервал, то на «пропущенных» кадрах UI бежит ~375, а панель композитит последний готовый кадр. Средний FPS резко растёт. Инфраструктура почти готова: `IGame.DesiredFPS` есть, backpressure-проверка в `RenderTargetGameOutput.CopyOutput:81` уже есть — не хватает rate-limit на самом рендере игры. Single-buffer при пропуске безопасен (нет записи во время сэмпла); double-buffer понадобится только если захотим, чтобы игра уходила вперёд UI.
2. **[СРЕДНЕ] Игру — на свой поток + отдельную GPU-очередь.** Перекрыть GPU игры (3.3 мс) с GPU UI. Но на одной GPU перекрытие ограничено, а зависимость по shared-surface всё равно частично сериализует. Рискованнее, ниже приоритет, чем #1.
3. **[МЕЛКО] GC в hot-path.** `GraphicsDevice.Submit` аллоцирует 5 `List`+`ToArray` на каждый сабмит (×2 сервиса × ~155/с ≈ 1500 всплесков/с); `BufferBarrier` аллоцирует `new[]{barrier}` на вызов. Запулить/переиспользовать. Steady-FPS не поднимет (упор в GPU), но уберёт GC-джиттер.
4. **[СДЕЛАНО] Кэш GPU-экспандеров заливки/обводки.** Раньше compute-экспандер каймы/ленты гонялся каждый кадр даже для статичной геометрии (+барьер +аллокация на контур). Теперь результат кэшируется и переиспользуется, пока геометрия/масштаб не изменились (dash-путь не кэшируется — анимируется). Небольшой выигрыш, уже в коде.

## Вывод
Узкое место — **рендер живой 3D-сцены в панель каждый кадр на одной очереди серийно с UI**, а не синхронизация. Самый безболезненный возврат — **ограничить частоту рендера игры-в-панели** (#1): панель не нуждается в 155 FPS, а UI без игры держит ~375.
