# Навигация с клавиатуры — дизайн и дорожная карта

Цель: до любого контрола можно добраться без мыши. Tab/Shift+Tab и стрелки вверх/вниз/влево/вправо,
причём **порядок обхода знает панель**, а не глобальный обходчик дерева: стопка знает, что её дети
стоят в линию, сетка — что у неё строки и колонки, wrap-панель — где кончается визуальная строка.
Глобальный обходчик всего этого не знает и обязан угадывать по координатам.

Это не клон WPF `KeyboardNavigation` с его режимами (`Continue`/`Cycle`/`Once`/`Local`), навешенными
attached-свойствами на контейнер. Мы берём суть — «спроси контейнер, куда идти» — и делаем её
**интерфейсом панели**, потому что у нас панель и так единственная, кто знает свою раскладку.

---

## Что уже есть в движке (на это опираемся, ничего параллельного не строим)

- **`FocusManager`** (`Adamantium.UI.Core/Input/FocusManager.cs`): `Focused`, `Scope`, словарь
  областей `focusScopes`, `CanFocus` (`IsEnabled && Visibility == Visible && Focusable`),
  `Focus(component, NavigationMethod, modifiers)`, `SetFocusScope`, `TryRestoreFocus`.
- **`NavigationMethod`** — `Unspecified / Directional / Tab / Mouse`. **Уже есть** и уже прокинут
  через `FocusManager.Focus` в `KeyboardDevice.SetFocusedElement`. Именно он потом отличит «фокус
  пришёл с клавиатуры» от «мышью» для показа рамки.
- **Клавиатурные события**: `Keyboard.PreviewKeyDownEvent` (Tunnel) и `KeyDownEvent` (**Bubble**),
  поднимаются `KeyboardDevice` на сфокусированном элементе. Всплытие доходит до окна — значит
  диспетчер навигации может стоять одним классовым хендлером, а не висеть на каждом элементе.
- **`Focusable`** на `InputUIComponent` (по умолчанию false; `ButtonBase` и `TextBoxBase`
  переопределяют метаданными на true).
- **`AncestorState`** (`Core/Input/AncestorState.cs`) — механика «состояние истинно, пока фокальный
  лист это элемент или его визуальный потомок». На ней сделан `IsMouseOver`, и в её же комментарии
  `IsKeyboardFocusWithin` назван следующим кандидатом. Переписывать не нужно, нужно применить.
- **Панели**: `Panel` (база), `StackPanel` и `WrapPanel` (обе `VirtualizingPanel`), `Grid`,
  `UniformGrid`, `DockPanel`, `Canvas`.

## Чего нет вообще

- Tab и Shift+Tab. `Key.Tab` не обрабатывается нигде. Нет ни `TabIndex`, ни `IsTabStop`, ни `MoveFocus`.
- Стрелочной навигации.
- `IsKeyboardFocusWithin` — поэтому составной контрол (`NumericUpDown`, у которого фокус берёт
  внутренний редактор) не может показать рамку на себе.
- Визуала фокуса как понятия: рамка не рисуется нигде, и нет различения «фокус с клавиатуры» и
  «фокус мышью».

## Ключевое решение: спрашиваем панель

```csharp
public enum FocusNavigationDirection { Next, Previous, Up, Down, Left, Right }

/// <summary>Панель, которая умеет сказать, кто следующий за её ребёнком в заданном направлении.</summary>
public interface INavigablePanel
{
    /// <param name="from">ПРЯМОЙ ребёнок этой панели, внутри которого сейчас фокус — не сам
    /// сфокусированный лист.</param>
    /// <returns>Кандидат (тоже прямой ребёнок) или null — «в этой панели дальше некому».</returns>
    IUIComponent Navigate(IUIComponent from, FocusNavigationDirection direction);
}
```

Две вещи, на которых всё держится:

1. **`from` — контейнер, а не лист.** Фокус может сидеть на кнопке в глубине шаблона; панели важно
   знать, через какого своего ребёнка этот фокус к ней относится.
2. **`null` — это не ошибка, а «выхожу за границу».** Диспетчер тогда поднимается к родительской
   панели и спрашивает её уже про наш контейнер. Так стрелка вправо, упершись в край стопки,
   естественно переходит в следующую колонку сетки — без единого знания о сетке внутри стопки.

## Диспетчер

`KeyboardNavigation` — статический класс, вешает **классовый хендлер на всплывающий `KeyDown`**.
Всплывающий, а не превью, — принципиально: клавиша сначала достаётся сфокусированному элементу, и
если он её обработал (каретка в тексте, значение у слайдера), навигация не вмешивается. Навигация —
это то, что осталось необработанным.

Алгоритм:

1. Клавиша → направление: `Tab` → `Next`/`Previous` (по Shift), стрелки → `Up/Down/Left/Right`.
2. От `Focused` вверх по визуальным предкам до первой панели с `INavigablePanel`, запоминая ребёнка,
   через которого вышли.
3. Спросить панель. `null` → подняться выше, `from` = наш контейнер в родительской панели.
4. Из кандидата спуститься до первого фокусируемого потомка (или взять сам кандидат).
5. Упёрлись в границу области фокуса: для Tab — завернуться по кругу, для стрелок — остановиться.
6. `FocusManager.Focus(target, NavigationMethod.Tab | Directional)`.

## Реализации по панелям

| Панель | Next / Previous | Стрелки |
|---|---|---|
| `Panel` (база) | `TabIndex`, иначе порядок `Children` | ТО ЖЕ САМОЕ — см. решение ниже |
| `StackPanel` | порядок `Children` | вдоль ориентации — сосед; поперёк — `null` |
| `Grid` | порядок `Children` | по строке/колонке из `Grid.Row`/`Grid.Column` |
| `UniformGrid` | порядок | по вычисленным строке/колонке |
| `WrapPanel` | порядок | вдоль линии — сосед; поперёк — ближайший по координате в соседней линии; перенос строки |
| `TabPanel` | порядок | вдоль полосы; поперёк — `null` |
| `DockPanel`, `Canvas`, всё прочее без формы | база | база |

**Решение по панелям без формы (заменяет фазу 3).** У `Canvas`, `DockPanel` и любой панели, которая
не переопределяет `Navigate`, нет ни строк, ни колонок — значит стрелке нечего значить, КРОМЕ
собственного порядка панели. Поэтому база отвечает одинаково и на Tab, и на стрелки: по `TabIndex`,
если автор его задал, иначе по порядку добавления детей. Заявляется один раз и работает для обоих
видов клавиш. Геометрический XY-поиск (как в WinUI) НЕ делаем.

## Что считается остановкой

`Focusable && IsEnabled && Visibility == Visible && IsTabStop` (последнее — новое свойство, по
умолчанию `true`).

Части шаблона исключаются тем, что шаблон сам ставит им `Focusable="false"` — как у `NumericUpDown`
кнопкам-степперам. Составной контрол должен быть **одной** остановкой: снаружи он не фокусируем, а
фокус берёт его редактор.

## Фокус внутри

Это тот самый хвост, из-за которого у `NumericUpDown` нет акцентной рамки.

- **`IsKeyboardFocusWithin`** — на `AncestorState`, ровно как `IsMouseOver`: Direct-события
  «вошёл/вышел» по цепочке предков сфокусированного элемента.
- **`IsKeyboardFocusVisible`** — визуал показывается только когда фокус пришёл с клавиатуры.
  Отличать по уже существующему `NavigationMethod` (аналог WPF `FocusVisualStyle` и CSS
  `:focus-visible`). Клик мышью фокус ставит, но рамку не зажигает.

## Визуал фокуса — ОДИН на все контролы, адорнером

Рамка фокуса не должна жить в шаблоне контрола. Шаблонов десятки, и стоит одному забыть — контрол
молча остаётся без визуала. Это ровно тот класс ошибок, который мы только что чинили переносом
`BorderBrush`/`CornerRadius` в `Control`: свойство, которое каждый объявляет сам, рано или поздно
кто-то не объявит.

Поэтому — **адорнер**, и вся инфраструктура под него уже написана:

- `Adorner : TemplatedUIComponent` с `AdornedElement`, который заодно становится родителем
  наследования, — тема-ресурсы (акцент) дотекают в адорнер сами.
- `AdornerLayer` уже держит отдельный слот под транзиентный `HoverAdorner` — фокусный ляжет туда же,
  тем же способом: один активный на окно.
- `SelectionAdorner` уже рисует рамку в паре пикселей СНАРУЖИ границ элемента — нужная геометрия
  готова, её остаётся повторить проще.
- Рендер уже кладёт `AdornerLayer.Adorners` поверх содержимого — значит рамка не обрежется у
  контрола с `ClipToBounds` и не будет спорить за место с его собственным содержимым.

**Как выглядит** (в духе UWP): прямоугольник по границам контрола, раздутый на `FocusVisualMargin`,
сплошная обводка `FocusVisualThickness` акцентного цвета, скругление — **из `CornerRadius` самого
контрола** (плюс тот же отступ), чтобы рамка повторяла форму, а не спорила с ней. `CornerRadius`
теперь на `Control`, так что читать его можно у любого контрола, не гадая.

**Ручки** (на `InputUIComponent`, чтобы были у всех):

| Свойство | По умолчанию | Зачем |
|---|---|---|
| `UseFocusVisual` | `true` | отказ для контрола, который показывает фокус сам (у `TextBox` уже акцентится своя рамка) |
| `FocusVisualBrush` | `{ThemeResource AccentFillColorDefault}` | цвет обводки |
| `FocusVisualThickness` | `2` | толщина |
| `FocusVisualMargin` | `2` | насколько рамка отступает наружу от границ |

**Кто зажигает**: центрально — `FocusManager`/диспетчер навигации, по `NavigationMethod`. Пришёл
фокус табом или стрелкой → `AdornerLayer.SetFocusVisual(element)`; мышью или фокус потерян →
снять. Ни один шаблон при этом не трогается.

UWP рисует двухтонную рамку (тёмная снаружи, светлая внутри), чтобы она читалась на любом фоне. Нам
это не нужно сразу, но раз место одно — добавить второй тон потом можно, не трогая ни один контрол.

### Готча визуала

Адорнерный слой принадлежит **окну**. У попапа своя поверхность (`PopupLayer`), и элемент,
сфокусированный внутри открытого попапа (список `DropDown`, меню), рамку на окне не получит — её надо
рисовать на слое того попапа. Проверить это надо в той же фазе, а не потом: `DropDown` — первый же
контрол, куда придут табом.

  - [x] `ListBox` — выбор + прокрутка;
  - [x] `TabControl` — Enter/Пробел открывает вкладку и шагает в её страницу, стрелки вдоль полосы;

- [ ] **Долг по адорнеру:** кольцо не может выступать за клипы НАД целью, и отступ применяется к
  размеру, но не к позиции — поэтому кольцо стоит по контуру, а не с зазором.

## Готчи, найденные ЗАМЕРОМ по ходу реализации

- **Содержимое попапа отцеплено от контрола визуально.** Клавиша, нажатая с фокусом внутри попапа,
  НИКОГДА не проходит через контрол, который его открыл. Отсюда правило для `DropDown`: фокус
  остаётся на заголовке, стрелки двигают строку, в список не заходим. Для меню/диалога наоборот —
  там фокусу место внутри, и выходить надо через Escape (см. фазу 4, не сделано).
- **Элемент, написанный как свой контейнер (`<DropDownItem/>`), — это КОНТРОЛ**, а контрол не может
  быть в двух местах: отдав его заголовку, список терял строку и прыгал размером. Заголовок обязан
  показывать содержимое контейнера, а не сам контейнер.
- **Стадия адорнеров рисует только с графическим устройством.** Перегрузка `RenderCache.Render()` без
  device не заводит батч-коллекторы — а через батч идёт любой темизированный `Border`, то есть всё
  кольцо целиком.
- **Клавиша выбрасывалась, если ничего не сфокусировано.** Окно открывается без фокуса, так что до
  первого клика клавиатуры не было вообще; окно теперь запасной адресат.
- **Адорнер режется собственным клипом цели** (`RenderParent` адорнера = сама цель). Введено
  `IUIComponent.ClippedByRenderParent`. ОСТАЛОСЬ: адорнер всё ещё не может выступать за клипы НАД
  целью, и его отступ применяется к размеру, но не к позиции — поэтому кольцо стоит по контуру.
- **Клавиатура быстро прокручивает список → состояния ЗАЛИПАЮТ на контейнерах.** Три разные причины,
  которые выглядят одинаково, и различать их надо замером, а не на глаз:
  1. *подсветка выбора* — выброшенный частичный проход кэша отрисовки гасил признак «геометрия
     устарела» через `Render`, и следующий полный обход считал контрол чистым, возвращая СТАРУЮ
     единицу (правка — вернуть признак; регрессия `DiscardedPartialPass_ReRecordsWhatItAlreadyRendered`);
  2. *наведение* — оно пересчитывается только при движении МЫШИ, а тут под неподвижным курсором едет
     содержимое; лечится пересчётом на осевшей раскладке (`MouseDevice.RefreshMouseOver`);
  3. *кольцо фокуса* — фокус был приколот к контейнеру, а контейнеры переиспользуются под другие
     строки; лечится тем, что место клавиатуры — строка (см. фазу 4).
  Общее правило: **состояние, привязанное к контейнеру, при виртуализации врёт.** Выбор, наведение и
  фокус обязаны принадлежать СТРОКЕ, а контейнер лишь показывает её.

## Готчи, которые видно уже сейчас

- **`TextBoxBase` ставит `Handled` на стрелки безусловно** — включая случай, когда каретка уже в
  конце строки. Значит из однострочного поля стрелкой вправо выйти не получится, пока редактор не
  научится отпускать клавишу на границе текста. Это фаза 5, но знать про это надо с фазы 1, иначе
  стрелки будут «не работать» именно там, где их сначала и попробуют.
- **Фокус сейчас ставится только в `FocusManager.OnPreviewMouseDown`,** и только при
  `e.OriginalSource == e.Source`. Мышиные события у нас `Direct` и поднимаются на каждом элементе
  цепочки отдельно (см. [[mouse-down-is-direct-not-bubbling]]) — при добавлении навигации это условие
  надо перепроверить, оно завязано на ту же особенность.
- **`FocusManager.Focus()` выставляет `Focused` ДО проверки области** и молча возвращает `false`,
  если области нет. Диспетчер навигации не должен полагаться на возвращаемое значение, пока это не
  приведено в порядок.
- **Панель может не иметь контейнера для элемента** (виртуализация). Навигация обязана это различать,
  иначе Tab будет проваливаться сквозь длинный список.
