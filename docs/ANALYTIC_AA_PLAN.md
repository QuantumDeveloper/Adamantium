# Аналитическое сглаживание (Analytic AA) — план

_Живой документ. Незакоммиченный артефакт. Ссылки на код — `путь:строка`._
_Решение: **сугубо GPU**, coverage/AA-fringe в стиле NanoVG/Skia. НЕ SDF-текстура, НЕ MSAA, НЕ пост-процесс. Геометрия обрабатывается на GPU (не на CPU). Начинаем с заливок._

---

## 0. Цель

Release-качество сглаживания краёв для произвольных 2D-форм Adamantium.UI **аналитически** (по покрытию пикселя краем), без MSAA-таргета и без SDF. Каждый граничный пиксель получает альфу = доля площади пикселя под формой → мягкая кромка ровно в ~1 device-пиксель на любом масштабе/зуме.

**Почему не текущее:** сейчас сглаживание = MSAA×4 на render-target (дорого по памяти — особенно на зуме дизайнера, см. деплой/VRAM сессии; даёт лишь 4 выборки/пиксель; не «честное» покрытие). Аналитика даёт истинное покрытие на 1 выборку и снимает зависимость от MSAA.

## 1. Текущее состояние (источник истины в коде)

Поток заливки (из `TRIANGULATION_STROKE_GPU_PLAN.md` §1):
```
Control.OnRender → DrawCommand+Payload → RenderUnit
  geometry.ProcessGeometry(Both)  // CPU even-odd parity триангуляция → Geometry.Mesh (треугольники)
  GeometryRenderer.Render()        // vtx/idx буфер → UIBasicEffect (VS+PS, UIBasicEffect.fx)
```
- Заливка — плоские треугольники (CPU-триангуляция, теперь Earcut O(n log n) — `Adamantium.Mathematics/Triangulation/Earcut.cs`), без атрибута покрытия/расстояния. PS выдаёт сплошной цвет×opacity.
- AA сегодня — только MSAA-resolve на RT.
- **GPU-compute-инфра УЖЕ реализована** (обводки) и переиспользуется нами:
  - `Adamantium.UI/Rendering/RenderUnits/GpuStrokeRenderComponent.cs` — шаблон: контур → BDA storage-буфер → compute (`StrokeExpand` / `StrokeDashCut`) пишет triangle-list в выходной буфер по BDA-адресу → barrier → `Draw`/`DrawIndirect`. PreRender дёргает compute из beforeRenderPass хука.
  - `Adamantium.Graphics/GraphicsDevice.cs` — `Dispatch` (:1337), `DrawIndirect` (:1343), `BufferBarrier`.
  - `Adamantium.UI/Effects/StrokeEffect.fx` — `StrokeExpandPass`/`StrokeDashCutPass` (compute) + `StrokeDrawPass` (VS+PS). `EffectShaderType.Compute` компилируется (Slang).
  - **AA в обводках пока НЕТ**: `StrokePS` = `return StrokeColor` (плоский), и в шейдере прямо помечено «proper outer-arc/transparency comes with **the AA pass**» (StrokeEffect.fx:190). Наш план — и есть эта AA-pass, общая для заливок и обводок.

## 2. Ядро идеи: покрытие края → альфа

Граничный пиксель должен получить `coverage ∈ [0..1]` = доля пикселя внутри формы, и `out.a = coverage * opacity` (premultiplied). Внутренние пиксели — `coverage=1`, внешние не растеризуются.

Вопрос «откуда PS берёт покрытие» — **главное решение** (см. §3), потому что аналитике нужна граничная информация (расстояние/покрытие), а её источник либо CPU (отвергнут), либо GPU (нужна инфра).

## 3. Где берём покрытие на GPU — РЕШЕНИЕ (нужно подтвердить)

### Вариант A — GPU генерит заливку + кайму (fringe), PS интерполирует покрытие  ← ведущий
Compute-ядро (часть единой GPU-системы геометрии) из контура формы строит:
- **тело**: треугольники заливки, атрибут `coverage = 1`;
- **кайму**: кольцо шириной ~1 device-px по контуру; внешние вершины `coverage = 0`, внутренние `coverage = 1`.

PS: `out = color; out.a *= coverage * opacity` (premultiplied). AA рождается линейной интерполяцией `coverage` поперёк каймы — аналитично и дёшево (1 выборка).
- ✅ согласуется с «геометрия на GPU» и единой системой линий (та же кайма, что у обводок).
- ✅ нет MSAA, нет SDF, нет пост-процесса.
- ✅ **инфра уже есть** — `GpuFillRenderComponent` зеркалит `GpuStrokeRenderComponent` (BDA-контур → compute-expander пишет тело+кайму → `Draw`); новый compute-проход в `StrokeEffect.fx`/новом эффекте; `StrokeVertex` + поле `coverage`. Compute уже умеет писать triangle-list по BDA — добавляем эмиссию каймы с альфа-атрибутом.
- ⚠️ перекрытия/самопересечения/вогнутые углы: каймы накладываются → двойной blend полупрозрачных → «швы». Решение — pass покрытия в stencil/одноканальный coverage-target (общая с обводками тема), затем единый composite. См. §5.

### Вариант B — аналитическое покрытие в PS по знаковому расстоянию (distance + fwidth)
Нести в вершинах атрибут расстояния до контура; PS: `coverage = saturate(0.5 + dist/fwidth(dist))`.
- ⚠️ корректный per-vertex distance-атрибут для произвольной триангуляции = граничная работа (по сути CPU или отдельный GPU-pass) — то самое, чего избегаем; для выпуклых форм проще, для путей — нет.
- Вывод: как общий механизм слабее A.

→ **Предлагаю A.** Подтверди A/B (и: AA — часть единой GPU-системы геометрии, т.е. через compute-инфру, или отдельный лёгкий путь?).

## 4. Корректность (общие правила, любой вариант)

- **Premultiplied alpha** на всём пути композитинга (иначе кайма даёт тёмный/светлый ореол).
- **Кайма в DEVICE-пикселях**: ширина ~1px после всех трансформов/зума (дизайнер рендерит design×scale — кайма не должна «толстеть» с зумом). Считать из производных позиции или из текущего scale.
- **Перекрытия полупрозрачных** не должны двойного-блендиться (§5).
- Согласовать с режимами заливки (`EvenOdd` / будущий настоящий non-zero, см. stroke-план §2-3).

---

## 5. Перекрытия и полупрозрачность (риск)

Fringe-подход корректен для непрозрачных форм, но при `opacity<1` накладывающиеся каймы (вогнутые углы, самопересечения, форма-на-форме одного цвета) блендятся дважды → видимые швы. Канонично — посчитать покрытие в отдельный **coverage/stencil-target** (max, не add), затем один composite формы с этим покрытием. Это та же задача, что у обводок в stroke-плане (Фаза C: stencil/coverage). Делать единым механизмом для заливок и обводок.

## 8. Верификация Фазы 1a (выполнено, 2026-06-23)

Реализовано: `FringeVertex` (POSITION+coverage), `FillFringeEffect.fx` (compute `FillFringeExpandCS` строит кольцо каймы по контуру через BDA + `FillFringeVS/PS` с `a*=coverage`), `GpuFillRenderComponent` (зеркало `GpuStrokeRenderComponent`), вязка в `RenderUnit.ProcessFillFringe` + `RenderUnitFactory` для Rectangle/Ellipse/Geometry. Тумблер `RenderUnit.UseGpuFill` (default true).

Headless A/B на красном прямоугольнике 100×80 (тело-заливка [50..150]), readback BGRA, правая кромка y=80:
- **Кайма рендерится наружу, покрытие линейно.** При `FringeWidth=5` (диагностика) x=150→155 дал B = 26,77,128,179,230 → **ровные шаги ~51 = линейная альфа 1→0**, направление наружу, знак `Winding` верный.
- **Кайма заменяет MSAA.** `FringeWidth=1`: «MSAA off + кайма» дал x=150 B=128 (50% бленд) — **идентично «MSAA×4»** (там тоже x=150 B=128). Без каймы тут был бы жёсткий red→white. На прямой кромке 1:1 разница с MSAA визуально неразличима (оба = 1 бленд-пиксель); выигрыш каймы — непрерывное покрытие (плавнее на кривых/диагоналях) + снятие MSAA-таргета (~4× VRAM, напрямую лечит OOM-на-зуме).

Текущее состояние: кайма + MSAA×4 держатся **вместе** (кайма на заливках, MSAA пока страхует обводки/текст/картинки). `FringeWidth=1.0`, MSAA назад `X4`.

Кайма = `1 device px / (worldScale·RenderScale)`. Проверено: на zoom 1 и 4 кромка остаётся ровно ~1 device-px (x=150 и x=600 → B=128), не растягивается.

### 1c полупрозрачность — ИЗМЕРЕНО и ОТЛОЖЕНО (2026-06-23)
Эмпирически (рендер над синим фоном):
- **Выпуклые/простые полупрозрачные** (rect Opacity=0.5) — УЖЕ корректны: кромка x=150 = `0.25·red+0.75·blue` = ровно один бленд (coverage 0.5 × opacity 0.5). Правила растеризации + общие вершины тела/каймы по контуру не дают двойного покрытия. Это 95% UI.
- **Двойной бленд только у самопересечений** (звезда-пентаграмма Opacity=0.5): вдоль внутренних линий R=166 (темнее) и R=96 (провалы).
- **Вывод про реализацию:** наивный coverage-RT (тело=1 + кайма + MAX) БЕЗ MSAA даёт ЖЁСТКУЮ внутреннюю кромку (тело растеризуется хардом) → РЕГРЕСС для частого случая. Корректный аналитический coverage без MSAA требует **inset тела на ~0.5px (polygon offset)** + straddle-кайму (±0.5px), тогда MAX в полосе кромки = ramp = гладко. Это отдельная крупная геом-задача (offset контуров) ради узкого выигрыша (полупрозрачные самопересечения). **ОТЛОЖЕНО** до возврата (понадобится и для полного снятия MSAA). Coverage-шейдеры были набросаны и откачены (см. git-историю FillFringeEffect.fx, если решим доделывать).
- **Known-limitation:** самопересекающиеся ПОЛУПРОЗРАЧНЫЕ заливки имеют швы вдоль внутренних линий. Непрозрачные — корректны.

## 9. Полупрозрачные самоперекрытия — покрытие ОБЪЕДИНЕНИЯ (2026-08-16)

Задача: одна полупрозрачная обводка, перекрывающая саму себя (самопересечение контура, шапки поверх тела дэша, диск скругления поверх ленты), смешивается с фоном ДВАЖДЫ и даёт тёмные жилы. Отдельные элементы, лежащие друг на друге, обязаны темнеть — это не тот случай.

**Как это решают ведущие движки.** Никто не вырезает перекрытия из геометрии — этот путь ломается на вырожденных случаях и T-стыках. Сходятся к двум схемам:
1. **Обводка → контур → заливка по правилу обмотки** (Skia, Direct2D): самоперекрытия схлопывает ненулевая обмотка, на GPU это трафарет-по-обмотке с последующей закраской, а сглаживание берут из MSAA.
2. **Накопление покрытия** (WebRender/Pathfinder, Vello): покрытие считают на пиксель в вычислительном шейдере по тайлам и смешивают ОДИН раз. Сглаживание остаётся аналитическим, MSAA не нужен.

Наш путь — третий: аналитическое покрытие прямо во фрагменте. Он безупречен на выпуклом и бесплатен, но **сам с собой не складывается**. Значит нужна схема 2 — но не тайловый конвейер целиком, а её суть: **посчитать покрытие объединения, смешать один раз**.

**Решение: глубина = максимум покрытия, трафарет = замок «писать один раз».**

Обоснование выбора — глубина и трафарет per-sample, поэтому схема работает и при MSAA, тогда как буфер покрытия на пиксель при MSAA даёт шов на каждом стыке ленты (первый четырёхугольник накрыл часть сэмплов и записал покрытие 1.0, второй увидел «больше не стало» и не внёс ничего). Плюс не нужны ни расширения, ни новая память.

**Два факта из кода, на которых стоит схема.** Глубина в UI **нигде не сравнивается** — все пять мест ставят `CompareOp.Always` — но все пять её **пишут** (z вершины = 0). И буфер глубины чистится в `1.0` на кадр (`BeginRendering`). Значит: запись глубины в этих пяти местах выключается (ничего не меняет — её никто не читает), и вся шкала глубины освобождается под покрытие.

**Окно глубины на обводку.** Каждая полупрозрачная обводка берёт из покадрового счётчика своё окно `base = 1 − k·span`, `span = 1/4096`, и пишет `base − coverage·span`. Окна идут ВНИЗ по порядку рисования, поэтому значение любой следующей обводки заведомо меньше всего, что уже лежит в буфере — тест `Less` проходит без единой очистки.

- **Проход 1** — только глубина: `SV_Depth = base − coverage·span`, тест `Less`, цвет замаскирован. По окончании в окне лежит минимум = МАКСИМУМ покрытия = покрытие объединения.
- **Проход 2** — та же лента: глубина `Equal` без записи, цвет с `alpha = coverage`. Проходит ровно тот фрагмент, чьё покрытие и есть максимум.
- **Ничьи** (внутри перекрытия оба дают 1.0 — это норма, а не редкость) снимает трафарет.

Трафарет здесь не сглаживает — он одноразовый замок; покрытие берётся из глубины и остаётся аналитическим. Прошлая неудачная попытка провалилась именно потому, что бинарным трафаретом решали ЗАДАЧУ СГЛАЖИВАНИЯ.

**Замок самоочищается, счётчик не нужен.** Трафарет делится на два поля одного буфера: метки групп инстансинга — младшие 7 бит, замок обводки — старший бит. Проход 1 ставит замок в 0 на каждом пикселе, которого касается (первый фрагмент на пикселе всегда проходит `Less` — окно ниже всего лежащего), проход 2 переводит его в 1 и тем отсекает остальных. Поэтому исходное состояние бита безразлично, а после обводки чистить нечего. Маски записи/сравнения разводят поля, и `Greater` у каёмок инстансинга работает как работал — только меток теперь 127, а не 255.

**Когда включается.** Только при `StrokeColor.a < 1` — непрозрачная обводка не видит своих перекрытий и платить за второй проход не должна. Исчерпание окон = откат к нынешнему поведению, не к артефакту.

**Ограничение.** Максимум покрытия — не точная площадь объединения: там, где две сглаженные кромки пересекают ОДИН пиксель, максимум занижает. Ошибка субпиксельная; это ровно тот компромисс, на котором стоят и Skia, и Vello.

**Потом — заливки (1c).** Та же оснастка закрывает и §5/§1c, но там нужен ещё `inset` тела на ~0.5px: у заливки тело растеризуется ЖЁСТКО, и максимум по жёсткому телу даёт жёсткую внутреннюю кромку. У обводки этой проблемы нет — у неё нет отдельного тела, каждый фрагмент ленты уже несёт аналитическое покрытие.

### Порядок работ
1. Аллокатор меток на `GraphicsDevice` → инстансинг переведён на него; проверка: рендер-тесты зелёные, кайма не изменилась.
2. `StrokeEffect`: проход `DrawDepth` (`SV_Depth = coverage`) + вариант `StrokePS` под тест `Equal`; проверка: покрытие вычисляется одним общим кодом, оба прохода дают бит-в-бит одно значение.
3. `GpuStrokeRenderComponent.Render`: при `a < 1` два прохода + метка; проверка: стенд «Translucent overlap» — самопересечения без жил, ДВА разных элемента по-прежнему темнеют.
4. Замер FPS на вкладке Shapes до/после; проверка: непрозрачные обводки не потеряли ни кадра.
