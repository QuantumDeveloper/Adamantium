---

## 0. Проблема

При анимации **размера** контрола (и смене геометрии вообще) каждый кадр меняется геометрия → `GpuFillRenderComponent`/тело/обводка **пересоздаются** = новые Vulkan-буферы (alloc + upload + dispose старых). Дорогая часть — именно **аллокация** (вспомни обводку: rebuild ~7.4ms из-за alloc/upload; `TryRepoint` убрал → 0.003ms, 2200×).

`TryRepoint` решил переиспользование при смене **униформ** (цвет/толщина/offset пера). Но при смене **геометрии того же размера** (ресайз прямоугольника с фиксированным радиусом топология не меняется — те же вершины, другие позиции) буфер всё равно пересоздаётся. Не должен.

---

## 1. Идея

1. **Перезаписывать, а не пересоздавать.** Если новый count ≤ ёмкости буфера — `Map`+`memcpy` (или re-dispatch компьютом для fringe) в существующий буфер. Без alloc.
2. **Выделять с запасом (over-allocation).** Не ровно под N вершин, а с headroom (бакеты/округление вверх, напр. до степени двойки или фикс-бакетов 64/128/256…). Тогда даже смена CornerRadius (±сегменты дуг) скорее всего влезает без переаллокации.
3. **Не ужимаемся (high-water-mark).** `Capacity` отдельно от `Count`; растём при нехватке, **вниз не реаллоцируем никогда**. После первого «пика» (макс. размер/сложность) контрол больше не пересоздаёт буфер — повторная анимация/смена радиуса бесплатны.
4. **Менеджер буферов.** Управление буферами **вынести из рендер-юнитов** в отдельный пул/менеджер; юниты только арендуют. Централизует ring для in-flight, рост ёмкости, переиспользование между юнитами.

---

## 2. Тиры обновления (общая модель)

1. **Чисто** (контрол не менялся) → кэш рендер-юнита, ноль работы. ✓ есть.
2. **Только униформы** → переставить униформы, буфер не трогаем. ✓ `TryRepoint` (обводки).
3. **Геометрия, count ≤ ёмкости** → **перезапись** в существующий буфер / re-dispatch. ← новое.
4. **count > ёмкости** → grow (реаллок до `count`+headroom, обновить `Capacity`), вниз не сжимаемся.

---

## 3. Менеджер буферов

`GpuBufferManager` (рабочее имя) владеет буферами; юнит держит **handle** (переиспользуемая аллокация), не сам `Buffer`.

- **`Rent(handle, requiredCount, usage)`** → гарантирует ёмкость ≥ requiredCount (grow с headroom, никогда не shrink), возвращает буфер текущего кадра (мапимый регион для CPU-данных / буфер для dispatch).
- **`Return(handle)`** при уничтожении юнита → буферы уходят в free-list пул (переиспользование между юнитами по бакету ёмкости).
- **Frames-in-flight.** `BuffersCount=3` → кольцо из N буферов на handle: каждый кадр пишем в **свой** слот (переиспользуется через N кадров по фенсу). Пересоздание сейчас «безопасно» только потому, что каждый раз свежий буфер; кольцо даёт ту же безопасность без alloc. (Оптимизация: для статичных буферов кольцо не нужно — ленивое «повышение» до ring только когда замечена per-frame перезапись.)
- **Политика роста.** `Capacity = max(Capacity, RoundUpToBucket(requiredCount))`. Бакеты ограничивают и waste, и частоту grow.
- **Владение/диспоз** уходит из юнитов (сейчас `ToDispose(Buffer.New(...))` в компонентах) в менеджер.

## 5. Нюансы

- **Fringe vertex buffer пишется компьютом** — CPU-memcpy не нужен, только re-dispatch в арендованный буфер; CPU-перезапись только у буфера точек.
- **Draw рисует actual `Count`, не `Capacity`** — over-allocation безопасна (буфер больше, рисуем сколько надо).
- **Статика vs анимация.** Статичная заливка создаётся один раз — ей кольцо не нужно; кост бьёт только на per-frame смене. Менеджер может держать 1 буфер пока статично и расширять до ring при активной перезаписи.
- **Когда count реально меняется:** анимация CornerRadius (число сегментов дуг), смена Path Data, size-adaptive тесселяция кривых. Headroom покрывает мелкие колебания; крупные → grow (один раз).
- **Скруглённый прямоугольник нельзя «transform-only»** (unit-quad + WVP-скейл): углы фиксированы в пикселях, при скейле поплывут. Поэтому именно перезапись вершин.
- **Память:** N×Capacity на handle. Для UI-геометрии (мелкие буферы) приемлемо; пул переиспользует между юнитами.
