## 0. Как это мерилось, и почему это первый раздел

Вопрос «нужен ли нам SIMD» трижды дал ПРОТИВОПОЛОЖНЫЕ ответы, прежде чем стенд стал честным. Числа ниже стоят
ровно столько, сколько стоит стенд, поэтому способы его испортить идут раньше результатов.

1. **Лямбда с захватом.** 64-байтная структура ездила через класс замыкания. `System.Numerics` вышел ВПЯТЕРО
   медленнее рукописного скаляра — число про стенд, не про SIMD.
2. **Debug.** JIT не встраивает интринсики, каждая операция над `Vector128` становится вызовом метода.
   **`rebuild.ps1` собирает в Debug**, поэтому его временные замеры несравнимы с Release.
3. **Неполное потребление результата.** Потреблялся только `M11`. Встроенный скалярный код JIT срезает как мёртвый
   (считает 7 операций вместо 112), а большой невстраиваемый метод — нет. Участники получали РАЗНОЕ количество
   выброшенного кода. Признак был физический: 3.40 нс на 112 операций = восемь операций за такт скаляром, чего
   не бывает.
4. **Недожатый тиринг — самый коварный, ловится ТОЛЬКО объёмом.** `System.Numerics.Matrix4x4` показывал 99 нс/оп на
   миллионе операций, 11 на десяти миллионах, 9.2 на ста; наши типы при этом держались ровно. Код CoreLib
   поставляется предкомпилированным (ReadyToRun) **без AVX** — образ AOT не знает целевой процессор. Векторизованная
   версия появляется только после порога перекомпиляции и фоновой перекомпиляции. Короткий прогрев мерит МЕДЛЕННЫЙ
   образ и выдаёт его за истину. Этот пункт дал не «неточность», а вывод с ОБРАТНЫМ ЗНАКОМ.
5. **Размер набора данных задаёт, что именно вы меряете.** N=4096 живёт в L1 и меряет арифметику; на миллионе
   элементов правит пропускная способность памяти, и выводы меняются (см. §4 против §5).

**Правило для любого будущего замера здесь:** Release; результат потребляется ЦЕЛИКОМ в выходной массив; прогрев
на МИЛЛИОНАХ вызовов + пауза + второй прогрев для каждого участника; два-три прогона со сверкой; проверка числа на
физическую возможность; и явный выбор размера данных под тот вопрос, который задан.

**Выводы:**

- **`System.Numerics.Matrix4x4` втрое БЫСТРЕЕ нашей**, а не медленнее. Ранняя редакция утверждала обратное —
  это был пункт 4 из §0.
- **Обёртка над ней — не тупик, а лучший из «по одной за раз»**: после встраивания это тот же код. Значит API
  `M11..M44` сохраняется целиком.
- **AVX стоит SSE** (9.5 против 12.7). Наша AVX-реализация идёт ВРОВЕНЬ с рантаймовской — потолок процессора.
- **FMA не выигрывает на матрицах** и остаётся позади AVX: цепочка зависимых `MultiplyAdd` длиннее по латентности,
  чем независимые умножения с деревом сложений. Единственный вывод, переживший все переделки стенда.
- **Указатели окупаются ТОЛЬКО на векторизованном ядре.** Контрольная строка это доказывает: на скалярном ядре
  закрепление не даёт ничего (26.7-27.6 против 27.6-38.4). Скалярное ядро упирается в арифметику, проверки границ
  теряются в её тени; векторное настолько быстрое, что индексация становится заметной долей.
- Наш скаляр *без* временной копии МЕДЛЕННЕЕ прошиваемого (42.7-50.6 против 34.6-36.2): писать по `out` по одному
  полю хуже, чем собрать локальную и скопировать 64 байта целиком.

## 3. Стык с нашими векторами: проверено утверждениями

| наш тип | рантаймовский | размер | вывод |
|---|---|---|---|
| `Vector4F` (`Sequential`, X/Y/Z/W) | `System.Numerics.Vector4` | 16 | совпадает побайтово |
| `Vector3F` (`Sequential`, X/Y/Z) | `System.Numerics.Vector3` | 12 | совпадает побайтово |
| `Matrix4x4F` (`Sequential, Pack=4`, `M11..M44`) | `System.Numerics.Matrix4x4` | 64 | совпадает побайтово |

Переход через шов — **переинтерпретация, а не пересборка**. Проверено не только по размеру, но и по значениям
(`Unsafe.As` туда-обратно) и по байтовому образу (`SequenceEqual` на 64 байтах), тест `WrapperStaysBlittable`.

**Что могло сломаться и не ломается — обойдено по коду:**

- **`ref` на поля матрицы (`ref m.M11`) — НИ ОДНОГО** во всём решении. Поля можно делать свойствами.
- **Индексаторы `[i]` и `[row, col]` — обычный `switch` по полям**, работают со свойствами без правок.
- **`unsafe`/`fixed`/`Unsafe.` внутри `Matrix4x4F` — нет вовсе.**
- **Рефлексии по полям (`GetFields`/`FieldInfo`) в графике, FX и компиляторе — нет.** Константы шейдеров не
  привязываются по именам полей.
- **`EffectParameter` делает `fixed (Matrix4x4F* p = values)`** — требует *unmanaged*-типа на этапе КОМПИЛЯЦИИ.
  Проверено ограничением `where T : unmanaged`: собирается. Плюс `Marshal.SizeOf` = 64 и шаг массива = 64 —
  выравнивание не подскочило, хотя рантаймовский тип внутри собран из `Vector4`-строк.
- **~50 сигнатур** (`LookAtLH`, `Billboard*`, `Translation(Vector3F)`, `RotationQuaternion`, `Decompose`,
  `Row1..Column4`, `Up/Down/Left/Right`, `TranslationVector`, `ScaleVector`) принимают и возвращают НАШИ
  `Vector3F/Vector4F/QuaternionF` — **ни одна не меняется**.

Препятствий не найдено. Риск не в векторах, а в объёме механической правки: 3470 строк `Matrix4x4F.cs`.

## 4. AoS против SoA, набор в L1 (N=4096): что даёт раскладка сама по себе

**AoS** (Array of Structures) — массив структур, как сейчас: `Vector3F[]`, в памяти `X0Y0Z0 X1Y1Z1 X2Y2Z2…`
**SoA** (Structure of Arrays) — структура массивов: три `float[]`, в памяти `X0X1X2… Y0Y1Y2… Z0Z1Z2…`

128-битный регистр держит четыре float. При AoS одна загрузка приносит X, Y, Z ОДНОГО объекта — три дорожки
заняты, четвёртая пропадает, а сложить их между собой можно только горизонтальными перестановками. При SoA одна
загрузка приносит X ЧЕТЫРЁХ разных объектов, и та же инструкция обрабатывает четыре тела без перестановок.

Операция — нормализация (три умножения, два сложения, корень, три деления). 100 млн операций, два прогона.

| участник | нс/оп | ускорение |
|---|---|---|
| AoS, скаляр (как сейчас) | 4.00-5.04 | — |
| **SoA, скаляр (КОНТРОЛЬ раскладки)** | 3.95-4.17 | **~1.0** |
| SoA + SSE, 4 тела за раз | 1.12-1.18 | 3.5x |
| SoA + AVX, 8 тел за раз | 0.69 | 6-7x |

**Контрольная строка — главная.** В L1 раскладка сама по себе не даёт НИЧЕГО. SoA не «быстрее» — SoA
**векторизуема**, и весь выигрыш приходит от кода, который поверх неё становится возможен.

Ширина конвертируется почти один к одному: SSE (4 дорожки) → 3.5x, AVX (8 дорожек) → 6-7x. Сравните с матрицами,
где AVX дал над SSE всего 1.3x: там ядро упирается в **перестановки дорожек** (`Permute`/`Shuffle`), и удвоение
ширины удваивает и перестановки. На SoA перестановок нет ни одной — дорожка `k` всё время обслуживает тело `k`.

## 5. AoS против SoA, миллион тел: когда правит память

Структура тела 64 байта (позиция, скорость, ориентация, сила, массы). AoS = 61 МБ. Шаг интегрирования трогает
позицию и скорость — 24 байта из 64.

| участник | схема доступа | нс/тело |
|---|---|---|
| AoS (структура 64 Б) | проход подряд | 6.80-8.07 |
| **SoA, скаляр (КОНТРОЛЬ)** | проход подряд | **4.14-4.53** |
| **SoA + AVX (8 тел за раз)** | проход подряд | **2.03-2.56** |
| AoS | случайный доступ | 14.7-19.3 |
| SoA | случайный доступ | 17.8-26.8 |

**При проходе подряд SoA читает МЕНЬШЕ, а не больше.** AoS тащит через шину всю структуру целиком (61 МБ), SoA
читает шесть нужных массивов (22 МБ) — втрое меньше трафика. Поэтому контрольная строка ведёт себя
**противоположно §4**: на миллионе тел раскладка сама по себе даёт **1.6-1.8x без единой SIMD-инструкции**.
Суммарно на проходе: 1.7x от раскладки × 1.9x от векторизации = **3.2-3.3x**, уже с учётом всей памяти.

**Поправка к ходячему утверждению «три промаха вместо одного».** Измеренная плата за случайный доступ —
**1.2-1.4x, а не 3x**: три промаха НЕЗАВИСИМЫ, процессор выпускает все три обращения сразу, и внеочередное
исполнение перекрывает их латентность.

**Но главное в этой таблице не про раскладку.** Случайный доступ стоит 14-27 нс против 2-8 у прохода подряд, для
ОБЕИХ раскладок. Схема доступа решает вчетверо больше, чем выбор AoS/SoA. Отсюда: решатель строят так, чтобы он
шёл ПОДРЯД (тела сортируют, ограничения группируют, острова связности раскладывают в непрерывные диапазоны) — не
ради SIMD, а ради этих 4x. А когда проход уже подряд, SoA выигрывает и по трафику, и по векторизации.

**Где AoS правильна:** подсистемы, которые дёргают по одному — взять трансформ узла по идентификатору, `Place()`
в UI. Там она у нас и стоит, и менять её незачем.

Компромисс, который берут на практике, — **AoSoA**: массив блоков по 4 или 8 тел, внутри блока SoA. Дорожки
заполнены, локальность сохраняется, объект остаётся отчасти цельным.

## 6. Что это даёт движку: счёт по коду

Счёт по количеству операций в коде × замеренная стоимость. Стенд 3D не поднимался, это **потолок, а не прогноз**.

| путь | умножений | на что |
|---|---|---|
| `Transform.CalculateFinalTransform` | **10** | на узел × камеру, когда узел движется. 8 из них — внутри `Matrix4x4F.Transformation`, это цепочка из восьми умножений |
| `AnimationHelper.InterpolateFrames` | **2** | на сустав в кадре |
| `AnimationController` — палитра | **1 + D** | на сустав, D = глубина в скелете |
| `OrientedBoundingBox.Transform` | 4 переноса вектора | на коллайдер × камеру |

Скиннинг на видеокарте (`jointIndices`/`jointWeights` в вершине, палитра уходит параметром `Bones`), поэтому на
процессоре только построение палитры — O(суставов), не O(вершин).

Экономия на одном умножении при переходе на AVX-по-одной: **~20 нс**.

| сценарий | умножений/кадр | экономия/кадр | доля бюджета 16.7 мс |
|---|---|---|---|
| 1000 движущихся объектов, 1 камера | 10 000 | 0.2 мс | 1.2% |
| 100 персонажей, 65 суставов, глубина 7 | 65 000 | 1.3 мс | 7.8% |
| 10 000 движущихся объектов, 2 камеры | 200 000 | 4.0 мс | 24% |

**Почему живой выигрыш будет меньше потолка:** 20 нс — пропускная способность тесного цикла по массивам в L1; в
движке матрицы приходят из разрозненных `Transform` и из `Dictionary<string, Matrix4x4F>`, где правит латентность
памяти. Ускоряется только арифметика — поиск по СТРОКОВОМУ ключу, конкатенация `ControllerId + JointSid` во
внутреннем цикле и `.Values.ToArray()` за кадр не ускоряются ни на грамм.

## 7. План

### Ф1 — дешёвое и безопасное, отдача больше, чем от SIMD на тех же путях

| # | что | почему | риск |
|---|---|---|---|
| 1.1 | `OrientedBoundingBox.GetCorners()` не должен делать `new Vector3F[8]` на каждый вызов | вызывается на узел × камеру × кадр из `IsInsideCameraFrustum`; ~120 Б на вызов = 7 МБ/с на 1000 узлах, 72 МБ/с на 10 000 | низкий |
| 1.2 | `BoundingFrustum.Contains` читает `planes[p][0..3]` через индексатор со `switch` — до 192 диспетчеризаций на узел × камеру × кадр | поднять `var pl = planes[p];` и читать поля напрямую | низкий |
| 1.3 | `OrientedBoundingBox.Transform` считает длину дважды: `axis.Length()`, затем `axis.Normalize()` | три лишних корня на коллайдер | низкий |
| 1.4 | `AnimationController.Update` строит палитру КВАДРАТИЧНО по глубине скелета | для J=65, D=7 это ~520 умножений вместо ~65 — **×8 по количеству операций**, больше, чем даёт SIMD. Нужен накопитель чистой цепочки: `Chain[j] = Interpolated[j] * Chain[parent]`, затем `FinalMatrices[j] = JointDictionary[j] * Chain[j]`. Напрямую переиспользовать `FinalMatrices[родителя]` НЕЛЬЗЯ — там лишний множитель `JointDictionary[родителя]` в начале. Заодно исчезает конкатенация строк во внутреннем цикле | средний — порядок умножения значим |

### Ф2 — SIMD внутрь нашего типа, API не меняется

| # | что | отдача | риск |
|---|---|---|---|
| 2.1 | тело `Matrix4x4F.Multiply` на `Vector256` | 27-30 → 9.5-10.5 нс | низкий: раскладка `Sequential, Pack=4`, поля `M11..M44`, `ref` на поля нет |
| 2.2 | `Vector4F.Transform` / `TransformNormal` / `TransformCoordinate` на `Vector128` | 6.2-6.5 → 2.0-2.5 нс | низкий |
| 2.3 | пакетные перегрузки `Vector3F.Transform*(массив)` — на указатели + AVX | ×4-5 вместо ×3, см. §1 | низкий, но применимо только там, где ЕСТЬ массив |

### Ф3 — решение о типе, отдельно и не срочно

`Matrix4x4F` можно сделать обёрткой над `System.Numerics.Matrix4x4`, поля — свойствами. Отдача та же, что у 2.1,
плюс вся остальная рантаймовская математика даром (инверсия, разложение). Стык проверен (§3), препятствий нет,
но правится сам тип на 3470 строк. **Делать только после Ф2, если Ф2 покажет, что этого мало.**

### Ф4 — если появится физика

Физики как подсистемы в движке НЕТ: ни твёрдых тел, ни решателя, ни интегратора, ни широкой фазы. Есть коллайдеры,
`Collision.cs` и отсечение по пирамиде видимости.

Если физика будет — **раскладка данных решается при проектировании, а не потом**. SoA (или AoSoA) даёт по §5
суммарно 3.2-3.3x на проходе подряд, и переделать её задним числом дороже, чем написать сразу. Цена SoA: объекта
больше нет, код индексный, случайный доступ на 1.2-1.4x дороже, вставка/удаление сложнее, с ООП-компонентами ECS
напрямую не стыкуется.

## 8. Чего НЕ делать — проверено, не тратить время повторно

| что | почему |
|---|---|
| переезжать на `System.Numerics` ради скорости МЕТОДОВ | она быстрее нашей втрое, но это и есть весь выигрыш; тот же результат даёт 2.1 без правки типа |
| писать отдельную ветку FMA для матриц | 12.2-14.0 против 9.5-10.5 у AVX — проигрывает |
| брать `Vector512` / AVX-512 | процессор не поддерживает (`V512hw=False`) |
