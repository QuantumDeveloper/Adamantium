> бюджет.** Намучились, повторять не будем.

## 1. Что осталось болеть

Эталонная сцена: Sandbox → вкладка Layout, виртуализированный ListBox из 600 цветных плиток, размер ячейки слайдером.

**Контейнерный оверхед ×3-4.** Каждая логическая плитка — это ≈3-4 `AdamantiumComponent`: `ListBoxItem` (контейнер +
chrome) → в его шаблоне `Border` + `ContentPresenter` → `Border` из `DataTemplate`. 600 плиток → ~1800-2400 полноценных
объектов layout+render. Это **множитель на каждую строчку затрат**, и единственная из пяти исходных бед, которая цела
целиком. Закрывается схлопыванием (§4c).

**А вот «командный буфер перезаписывается каждый кадр» бедой больше не считается.** Запись сведена инстансингом к
горстке instanced-draw, это микросекунды — по тому же доводу, по которому в §6 отвергнута многопоточная запись внутри
кадра. Кешировать нечего, пока замер не покажет обратного.

> Цифры — в §0 «БАЗОВАЯ ЛИНИЯ» (15.08.2026). Те, с которых начинался документ, сняты до удержания юнитов и грязноты и
> как основание для решений негодны, поэтому здесь не приводятся.

Целевой инвариант неизменен: **стоимость кадра должна быть O(того, что изменилось), а не O(размера дерева).**

## 3. Цели / критерии успеха

- Статичный кадр UI → **~0 CPU** в build/proc (только present).
- Драг слайдера по 600 плиткам → платим только за плитки, которые реально сдвинулись/изменили размер, а не за всё дерево.
- Предсказуемость: стоимость — функция набора изменений, измеримая и ограниченная.
- Никаких stale-рендеров (нынешняя каша «призрак/наложение» при быстром ресайзе должна **раствориться**, а не патчиться — правильно dirty-трекнутый retained-кэш не может оставить устаревший юнит на экране).
- Фундамент, совместимый с инстансингом по идентичности геометрии для не-SDF геометрии — СДЕЛАН (§7).

## 3a. Переформулировка: рендер НЕ «воспроизводит структуру дерева»

Дерево компонентов зеркалилось в рендер по ОДНОЙ причине — воспроизвести визуал контролов на экране. Но зеркалирование — не цель, а ленивая реализация, и она не даёт нормального перфа (O(дерева)/кадр).

**Задача рендера — воспроизвести итоговую КАРТИНКУ, а не структуру дерева.** Значит нужен механизм, который держит **retained-сцену визуала** (плоский display-list из инстанс-пейлоадов) и **инкрементально её патчит**, а НЕ пере-обходит дерево каждый кадр:
- **Дерево компонентов = ИСТОЧНИК** (layout / интеракции / эмит пейлоадов), а не структура рендера.
- **Рендер-сцена = отдельная retained-структура**: строится по мере появления контролов, патчится по dirty, рисуется батчами. Per-frame обхода дерева нет вовсе.
- Прото (чтобы не изобретать вслепую): WPF ретейнит рисование per-`Visual` (записал раз → инвалидация перезаписывает) и композит отдельно; Flutter — `Layer tree` как эффективное render-представление, отвязанное от Widget-дерева. **Наш твист сверх этого**: инстансинг-по-умолчанию + батч по идентичности геометрии + схлопывание шаблона айтема в один пейлоад.

## 4. Модель: инстансинг по умолчанию (ядро дизайна)

Ядро — предложение: **рендеринг фреймворка инстансинговый ПО УМОЛЧАНИЮ.** Никогда не «настоящий immediate mode». Всегда ищем повторение геометрии и батчим всё возможное. Ожидаем ЛЮБУЮ геометрию (не только SDF-прямоугольники).

**Инверсия модели юнита (ключевая идея):**
- **Было**: N юнитов, у каждого свой единственный payload + своя машинерия (триангуляция / fringe / stroke); батч собирается оппортунистически в конце `Render` (`RectBatchCollector` / `TextBatchCollector`).
- **Станет**: юнит ключуется **идентичностью геометрии** (тесселированный меш ИЛИ SDF-программа) и держит **растущую коллекцию per-instance payload'ов** (трансформ, цвет, clip, толщина обводки…). Компонент, который хочет нарисовать эту геометрию, просто **докидывает свой инстанс** в коллекцию соответствующего юнита — а не собирает собственный тяжёлый юнит. Внутри одного батчнутого юнита лежат ВСЕ данные для корректной отрисовки всех его инстансов.

Что это даёт:
- **Дедуп триангуляции**: повторяющийся кастомный `Path` тесселируется ОДИН раз (его идентичность), все инстансы делят один vertex/index-буфер. Огромный выигрыш для повторяющейся не-SDF геометрии — уходит лишняя триангуляция.
- **Меньше объектов**: компонент вносит ИНСТАНС (маленький struct), а не тяжёлый юнит с триангуляцией/fringe/stroke на каждый.
- **Батч по умолчанию**: всё, что делит геометрию, батчится автоматически; immediate mode не наступает.
- Прямое продолжение существующего: `RectBatchCollector` (SDF-подложки) и `TextBatchCollector` (глифы) уже делают это оппортунистически. Здесь мы поднимаем это в **первичную, retained, geometry-keyed** модель для ВСЕЙ геометрии. Совпадает с задумкой инстансинга по идентичности геометрии, и она уже реализована (§7): инстансный меш + per-instance {transform, color} через BDA + инстансный analytic-AA fringe (шаблон — `FillFringeEffect`/`StrokeEffect`, storage-by-address по uint64).

### 4a. Инстансинг и dirty-трекинг = ОДИН механизм
Инстанс-буфер геометрии — это и есть **retained-состояние**. Поэтому два «столпа» не разные, а один:
- Компонент сдвинулся / сменил цвет → **патчим его инстанс** в буфере по индексу/оффсету (маленькая запись). Dirty = точечный патч инстанса, O(1) на изменение — не пересборка.
- Добавился / удалился компонент → добавить / освободить инстанс (компактизация или free-list в буфере).
- Ничего не изменилось → инстансы не трогаем → **пере-submit** (fast-path чистого кадра).

Так «инстансинг по умолчанию» + «агрессивный dirty» = инстанс-буферы держат состояние, dirty патчит конкретные инстансы, чистый кадр стоит ~0.

### 4b. Порядок отрисовки и z-order — ✅ РЕШЕНО сегментацией

Проблема была реальная: один draw всех инстансов геометрии G ломает painter-порядок, если между ними по z должна
оказаться другая геометрия H. **Выбрана сегментация по paint-order, она в коде** (`BatchCollector<T>` + ранги с
зазорами). Раздел оставлен ради разбора, почему остальные кандидаты отпали.

- **Сегментация по paint-order — ПРИНЯТО.** Идём в порядке отрисовки, докидываем инстансы в активный коллектор; **флашим**, когда появляется другая геометрия, которая ПЕРЕСЕКАЕТСЯ, либо меняются ножницы. Непересекающиеся инстансы одной геометрии (плитки списка, глифы — типичный UI) сливаются в один draw, порядок внутри не важен.
- **Z-bucket + depth-test — отвергнуто.** Per-instance Z из paint-order + буфер глубины: непрозрачное можно переупорядочивать свободно. Но UI почти весь на альфа-смешивании и аналитической кайме (прозрачные края) → порядок «сзади вперёд» обязателен, и глубина как ЕДИНСТВЕННЫЙ механизм не годится. (Глубину мы с тех пор всё же используем — но как временную рабочую память в одном проходе обводки, а не как замену порядку; см. `ANALYTIC_AA_PLAN.md` §9.)
- **Гибрид — не понадобился:** сегментация уже даёт его поведение, а отдельного механизма не заводит.

Следствие для «юнит = коллекция инстансов»: retained per-geometry юнит идеален, пока инстансы disjoint (списки/сетки/текст). Для декорированного перекрывающегося виджета (кнопка: фон+рамка+текст в одной точке) разные геометрии по z обязательны → это не один общий batch, а сегменты / мелкие per-виджет батчи. **Значит draw-порядок — это последовательность (geometry, instance-range, clip)-сегментов, а не глобально-один-batch-на-геометрию.**

### 4c. Схлопывание контейнеров — ⚠️ ПОД ВОПРОСОМ, требует пере-обоснования замером

> **Довод, с которого это начиналось, почти весь закрыт другими средствами.** Раздел оставлен как дизайн на случай,
> если замер подтвердит нужду; начинать работу без такого замера — нельзя, это самая дорогая часть плана.
>
> Исходно: логическая плитка = 3-4 компонента (`ListBoxItem` → `Border` + `ContentPresenter` → `Border` из шаблона
> данных), 600 плиток = 1800-2400 объектов, множитель на всё. С тех пор «всё» разъехалось на четыре статьи, и три
> закрылись без схлопывания:
>
> | статья | чем закрыта |
> |---|---|
> | число вызовов отрисовки | инстансингом: плитки сходятся в один SDF-батч, звёзды — в один instanced-draw |
> | обход дерева каждый кадр | грязнотой: `Clean` не обходит ничего, `Partial` правит на месте, `Structural` трогает только вошедшее и ушедшее |
> | стоимость РАСКЛАДКИ | **ничем, и схлопывание её не трогает** — раскладка идёт по компонентам, а схлопывание это рендер-сторона. Четыре компонента будут мерены и расставлены, даже если дадут один пейлоад |
> | структурные проходы + память | НЕ закрыта: при прокрутке реализация/снятие контейнеров обрабатывает 1800 объектов вместо 600 |
>
> **Что мерить перед решением:** сколько компонентов на айтем у нас на самом деле и сколько из них вообще ЧТО-ТО
> рисуют. `ContentPresenter` без фона юнитов может не давать вовсе — тогда множитель по рендеру давно не ×4, а ×2, и
> цена работы перестаёт окупаться.
>
> **Чем схлопывание ХОРОШО, если делать:** оно ничего не отнимает у автора разметки. Шаблон остаётся каким написан, а
> схлопывание — внутренний проход обработки (§4d). Это отличает его от «положите меньше элементов в шаблон», что
> решением не является в принципе: фреймворк с богатыми возможностями не может отвечать «не пользуйтесь ими».

#### Исходный дизайн (если замер подтвердит нужду)
Сейчас `BuildFromVisualTree` зеркалит дерево 1:1 — каждый из ~1800 компонентов даёт свои юниты. Ключевой сдвиг: **структура рендер-юнитов должна ОТВЯЗАТЬСЯ от дерева компонентов.** Повторяющийся шаблон айтема (его 3-4 контейнера: `ListBoxItem` + `Border` + `ContentPresenter` + `Border`) **схлопывается в ОДИН пейлоад**, а не остаётся набором отдельных render-элементов.

Разделение ответственности:
- **Дерево компонентов** остаётся — для layout, hit-test, темплейтинга, интеракций (селекция на `ListBoxItem` и т.п.). Его не удаляем.
- **Рендер-представление** — плоское: набор `(render-шаблон → инстанс-буфер)`. Один айтем = ОДИН параметризованный пейлоад его целого визуала (фон-rect + рамка + контент), а не 3-4 юнита.

Мост между ними: когда layout айтема устаканился, он **эмитит/обновляет один параметризованный пейлоад** (весь свой визуал) в рендер-кэш. Dirty на айтеме → патч этого одного пейлоада. `DataTemplate`/`ItemsControl` дают естественную границу схлопывания: все айтемы делят один шаблон → один render-шаблон, N инстансов.

Выигрыш в **худшем сценарии**: обрабатываем 600 пейлоадов, а не 1800 компонентов; per-frame рендер-обход дерева уходит вовсе (рендер работает от шаблонов+инстансов, а не от компонентов). Это то самое «упростить структуру и уменьшить время обработки кадра в worst-case».

Сложности (обсуждаем):
- **Что схлопывается.** `DataTemplate`-айтемы с фиксированной структурой — явный кейс. Произвольная вложенность контейнеров — сложнее (нужен признак «это повторяющийся шаблон»).
- **Переменный контент внутри пейлоада.** Цвет/размер — простые per-instance параметры. **Текст** (переменные глиф-раны) — самое сложное: его нельзя тривиально запихнуть одним параметром; вероятно текст остаётся отдельным (суб-)батчем глифов, привязанным к инстансу.
- **Частичные изменения внутри айтема** (сменился цвет одного дочернего) → патч соответствующей части пейлоада.

### 4d. Эргономика vs скорость: слияние — это ОБРАБОТКА, а не забота юзера (ЖЁСТКОЕ требование)
**Невозможное, которое обязаны сделать: сохранить простоту/удобство API И быть мегабыстрыми на самых нагруженных сценах.** Значит: **юзер (автор контрола) НЕ сливает ничего в один пейлоад и не вводит «миллионы параметров».** Он рисует через `DrawingContext` как привычно — отдельными естественными вызовами `DrawRoundedRect(...)`, `DrawText(...)`, `DrawGeometry(...)`. Разные пейлоады остаются на стороне юзера / самого drawing-контекста. Слияние — **внутренний проход обработки**:

1. **Гео-уровень (авто, без участия юзера).** Каждая нарисованная геометрия получает стабильную идентичность (хэш формы, без трансформа). Одинаковая геометрия → общий vtx/idx + один инстанс-буфер → один instanced-draw. Уже это батчит 600 плиток-`Border` в один draw, все глифы и т.п. — большая часть выигрыша БЕСПЛАТНО, поверх текущего API.
2. **Структурное схлопывание айтема (агрессивный сверх).** Граница `DataTemplate`/`ItemsControl` говорит «все айтемы = один шаблон» → поток команд одного айтема регистрируется как **render-шаблон** один раз, а каждый айтем = ОДИН компактный инстанс-рекорд (только меняющиеся параметры).

Ключевое: **параметры инстанса — это ровно те аргументы, что юзер УЖЕ передал** в `DrawRoundedRect` (позиция из layout, цвет, радиус). Мердж их ИЗВЛЕКАЕТ в инстанс-буфер; руками их никто не вводит. Ноль доп. нагрузки на API.

Контракт рендера контрола остаётся immediate-выглядящим (`Render(ctx)` пишет команды как сейчас); проход мерджа **диффит** новый поток команд против retained-вклада этого контрола и **патчит только изменившееся** (и запускается только для dirty-контролов). Юзер пишет просто — движок держит retained-инстансную сцену.

> Это заменяет ложную развилку из §4c (a «вывод из шаблона» vs b «контрол декларирует пейлоад»): не нужно НИ то, ни другое на стороне юзера — контрол просто рисует, а идентичность/инстансинг/схлопывание делает проход мерджа.

Прото: **Skia** так и работает — эргономичный canvas (`drawRect`/`drawPath`), а op-batching сливает совместимые операции в батч-дро внутри; юзер про это не думает. Наш твист сверху — **retained** (патч по хэндлу) + **схлопывание шаблона айтема**.

### 4e. Идентичность геометрии и дифф потока команд (решено)
- **Идентичность = форма + размер.** Цвет НЕ входит (per-instance). Трансформ/позиция — per-instance.
- **Обводка — в идентичности.** Те же параметры геометрии → та же обводка: fill+stroke одной формы = ОДНА identity, инстансятся вместе. Если контрол ЯВНО задал другую обводку → отдельная identity / отдельная отрисовка. (Цвет обводки — per-instance, как fill.)
- **Дифф потока команд — ПОЗИЦИОННЫЙ (по номеру команды), не по ключу.** i-я команда контрола ↔ i-й слот его вклада в сцену. Ключ, повторяющий глубину дерева, делать сложно и не нужно.
  - *Оговорка:* если контрол УСЛОВНО эмитит разное число команд (пропустил при null) — позиционное сопоставление сбивается. Решаем «стабильным порядком эмита» (контрол всегда шлёт одинаковую последовательность; невидимое = флаг/пустой инстанс, а не отсутствие команды), либо версионируем структуру вклада и при её смене пере-эмитим весь вклад контрола (а не патчим).

### 4f. Распознавание повторяющегося шаблона — НЕ через DataTemplate
Проблема (подмечено): `DataTemplate` существует только как артефакт биндинга. Контролы могут быть созданы **в коде без всякого биндинга** — тогда сигнала «это шаблон» нет.

Решение: **схлопывание опирается на СТРУКТУРНЫЙ ФИНГЕРПРИНТ эмитнутого потока**, а не на `DataTemplate`. Фингерпринт = последовательность geometry-identity + структура вклада (БЕЗ instance-параметров: без цвета/позиции). Поддеревья с одинаковым фингерпринтом = один render-шаблон → схлопываются в инстансы. `DataTemplate` становится лишь **подсказкой** («эти точно совпадут — можно не детектить»), а не требованием. 600 одинаковых `Border`, созданных циклом в коде, фингерпринтятся идентично и схлопываются так же.

Важно про два уровня:
- **Level 1 (гео-мердж) работает ВСЕГДА** — батчит draw'ы по identity независимо от того, как созданы контролы.
- **Level 2 (схлопывание)** нужен для снижения CPU-обработки (600 инстансов вместо 1800 компонентов) и опирается на фингерпринт, не на биндинг.
- Фингерпринт считаем не каждый кадр, а при СТРУКТУРНОМ изменении (add/remove); дальше — патч инстансов. Амортизируется.

### 4g. Ключ контрола вместо хэширования потока (предложение)
Чтобы не хэшить поток команд и не рисковать коллизиями — **контрол сам даёт стабильный ключ**. Но тут критично различать ДВА ключа (иначе группировка ломается):

- **`TemplateKey` (структурный, ОБЩИЙ у одинаковых контролов)** — то, что группирует инстансы. Одинаковый ⟺ одинаковая СТРУКТУРА отрисовки: тип контрола + render-влияющая конфигурация (есть/нет обводки, тип углов, число под-примитивов…), **БЕЗ instance-параметров** (цвет/размер/позиция НЕ входят). Именно он делает фингерпринт устойчивым: группировка = словарь по `TemplateKey`, без структурного сравнения.
  - ⚠️ Если сделать ключ УНИКАЛЬНЫМ на экземпляр — схлопывание не сработает (каждый контрол «сам по себе»). Для Level 2 нужен именно ОБЩИЙ структурный ключ.
- **`InstanceHandle` (у каждого экземпляра, стабильный)** — его слот в инстанс-буфере шаблона, чтобы патчить по dirty. Тут уже уникальность на экземпляр (сегодня это `RenderId`).

Контракт: **одинаковый `TemplateKey` ⟺ одинаковая последовательность команд/identity.** «Дал один ключ разным структурам» = баг (сломанное схлопывание); «разные ключи одинаковым» = просто перф-промах (медленнее, не сломано). В debug валидируем: `TemplateKey` совпал ⟹ вычисленный фингерпринт совпал (ловит ошибку автора). Фингерпринт остаётся fallback'ом для ad-hoc `DrawingContext` без контрола.

Важно для §4d: `TemplateKey` — **забота АВТОРА КОНТРОЛА (сторона фреймворка)**, не прикладного юзера. Контролов мало и они наши; app-разработчик ключей не касается — простота API цела.

### 4h. Управление инстанс-буфером — ✅ СДЕЛАНО, но НЕ так, как здесь предлагалось

> **Что в коде.** Буфер удерживается между кадрами и патчится по слоту: `BatchCollector.UpdateSlot` пишет ОДИН инстанс
> на месте, карты `_rectSlotByUnit` / `_sdfSlotByUnit` / `_textRunByUnit` играют роль «id → слот», сегменты
> переигрываются `DrawRecordedSegment` без пере-бейка, а освободившиеся диапазоны возвращаются в `_freeBlocks` и
> переиспользуются (`AllocateSegment`, `ReplaceInSegment`, `RepointSegment`).
>
> **Чего НЕ случилось:** swap-remove и сжатия массива. Единицей удержания стал СЕГМЕНТ с собственной вместимостью, а
> не отдельный слот в плотном массиве — потому что сложность, как и предупреждал сам план, оказалась не в массиве, а в
> границах сегментов: они решаются во время обхода (смена ножниц, перекрытие), и удерживать надо именно их. Ниже —
> исходное предложение, оно осталось верным по духу и неверным по форме.

Инстанс-буфер на identity = **плотный массив + карта `RenderId → slot`** (паттерн sparse-set / packed array из ECS):
- **add** → append в конец, `map[id] = slot`.
- **remove** → **swap-remove**: последний инстанс переезжает на освободившийся слот, буфер сжимается на 1; `map` обновляется для переехавшего id. O(1), без дыр → сегмент draw = чистый непрерывный диапазон.
- **patch (dirty)** → `map[id]` → запись в слот. O(1).
- **draw** → непрерывный диапазон, без пропусков.
- *Порядок в буфере:* для сливаемого сегмента инстансы disjoint по построению (перекрытие → флаш в отдельный сегмент, §4b) → порядок внутри свободен → swap-remove корректен. Виртуализация **рециклит** слоты (patch, не remove) → churn удаления низкий.
- *(Если понадобится держать порядок внутри сегмента — вариант free-list + «мёртвый» флаг вместо swap-remove; по умолчанию swap-remove.)*

### 4i. Dirty-пайплайны — ДВА кооперирующих, упорядоченных ✅ СДЕЛАНО
- **Layout-dirty** (`LayoutManager`: style/measure/arrange) — как есть.
- **Render-dirty** — набор компонентов, чей вклад в сцену надо пере-эмитить/пропатчить. Живёт **внутри `RenderCache`**
  (`_geometryDirtyBuffer` / `_paintDirtyBuffer` / `_partialDirty`), отдельного менеджера НЕТ и не нужно: он был бы
  вторым механизмом рядом с тем, что уже работает.
- **Связь:** arrange, изменивший позицию/размер → метит компонент render-dirty; свойство с `AffectsRender` → напрямую.
- **Порядок в кадре:** сперва layout, ПОТОМ обработка render-dirty. Итог кадра классифицируется `RenderBuildKind`:
  `Clean` (ничего) → `Partial` (правка на месте) → `Structural` (сплайсинг вошедшего/ушедшего) → `Full` (полный обход,
  только как запасной). `proc` пропускается на `Clean` и на `Partial` без движения.
- **Почему не один:** разная гранулярность и жизненный цикл, и layout ОБЯЗАН предшествовать рендеру.

### 4j. Как per-instance данные попадают в шейдер

> Здесь было записано, что BDA-разыменование по указателю работает только в compute, а в graphics-стейджах ломается.
> **Это больше не так** — ограничение снято, BDA живёт по всему движку, включая graphics. Формулировку выбросили,
> чтобы она не влияла на решения.

**Как сделано — вопрос закрыт:** батчи читают per-instance из **BDA-буфера по `SV_InstanceID`**, вершинного ввода у них
нет вовсе, квад берётся из `SV_VertexID`. То есть выбран BDA, а не descriptor-heap-SSBO: форма со `StructuredBuffer` по
`SV_InstanceID` на этом устройстве не читалась, и об этом сказано в комментарии шейдера.

**Требует device-фич:** `shaderDrawParameters` (для `SV_VertexID` / `SV_InstanceID` — Slang эмитит capability
`DrawParameters`, без фичи `vkCreateShadersEXT` отвергает шейдер), descriptor_heap.

### 4k. Cache locality / data-oriented (первоклассная цель)
Нынешняя беда не только в O(дерева) операций, но и в **cache-hostile** доступе: обход указательно-связанного дерева разбросанных по куче объектов + виртуальный `Render()` на каждом узле → промах кэша на каждый компонент. Переписка чинит ОБА: меньше операций (только dirty) И **непрерывные данные**.

- **Горячие per-frame данные — плоские непрерывные массивы.** Инстанс-параметры и `DrawList`-сегменты — contiguous → hot-циклы (re-bake, submit) идут последовательно, префетчер счастлив.
- **Sparse-set уже это даёт (§4h):** ПЛОТНЫЙ массив инстансов итерируется (draw/re-bake) кэш-дружелюбно; РАЗРЕЖЕННАЯ карта `id→slot` — random-access, но её трогаем только на patch/add/remove, НЕ в draw-цикле.
- **SoA vs AoS — по паттерну доступа.** Массовый re-bake (драг двигает ВСЕ плитки → пишем только трансформы) выигрывает от **SoA** (`transforms[]` отдельно — не тащим color/corner в кэш-линию). Патч одного инстанса цел (сменился цвет) — AoS-дружелюбен. Вероятно: часто-массово-обновляемое (трансформ) в своём массиве, остальное отдельно. Уточняем при реализации.
- **Dirty обрабатываем в порядке слотов/буфера** → локальность записи.
- **Холодное/структурное** (реестр геометрий, `id→slot`, фингерпринты) — отдельно от горячего, трогается на структурных изменениях, не в кадре.

Синергия: cache locality + O(изменений) = не «просто меньше работы», а «меньше работы, и она кэш-локальна» → вот откуда «мегабыстро на нагруженных сценах». Держим этот принцип во ВСЕХ фазах §6.

**НО не в ущерб архитектуре.** DOD/плоские массивы/SoA — это **деталь реализации ГОРЯЧЕГО хранилища**, спрятанная за чистыми абстракциями (напр. `InstanceBuffer<T>`: внутри dense/SoA, снаружи — хэндл-API), а не философия, заражающая весь код. Границы модулей (`GeometryRegistry`, контракт эмита, API контролов из §4d) остаются чистыми/ООП и тестируемыми. Локальность оптимизируем ТАМ, где она горячая и замерена, — не «ради флэт-массивов везде».

### 4p. ОДИН путь для геометрии: несимметричные углы, пунктир, дуги и недостающие примитивы — всё в SDF

**Почему это важнее, чем звучит.** Прямоугольники и эллипсы — порядка 90% всей геометрии интерфейса. Всё, что выпадает
из SDF-батча, уезжает на по-юнитный путь: тесселяция меша плюс машинерия аналитической каёмки на КАЖДЫЙ экземпляр. То
есть каждый отказ — это не «чуть медленнее», а переход в другой класс стоимости.

**Что выбрасывает сегодня** (проверено в коллекторах, 15.08.2026):

| отказ | где | насколько частый случай |
|---|---|---|
| **несимметричный радиус углов** | `c.TopLeft == c.TopRight && ...` в четырёх коллекторах (`RectBatch`, `Gradient`, `Pattern`, `Fractal`) | заголовки вкладок (скруглены сверху), первый/последний элемент сгруппированного списка, выноски, части риббона — постоянно |
| **пунктирная / обрезанная обводка** | `IsPenBatchable` | пунктирные рамки, индикаторы прогресса |
| **дуга и сектор эллипса** | `p.StartAngle <= 0 && p.SweepAngle >= 360` | кольца прогресса, спиннеры. В коде отмечено `TODO(arc)`: шейдер вырезать клин УМЕЕТ (`EllipseData.Arc`), но батчинг дуг терял устройство и остался выключенным |

**Что делать — свести всё в один путь, а не расширять список исключений:**

1. **Четыре радиуса в SDF.** `CornerRadius` у нас — четыре скаляра, углы круговые, значит подходит точная стандартная
   формула, две выборки без ветвлений:

   ```hlsl
   float sdRoundedBox(float2 p, float2 b, float4 r)
   {
       r.xy = (p.x > 0.0) ? r.xy : r.zw;
       r.x  = (p.y > 0.0) ? r.x  : r.y;
       float2 q = abs(p) - b + r.x;
       return min(max(q.x, q.y), 0.0) + length(max(q, 0.0)) - r.x;
   }
   ```

   В записи нужно поле `float4 Radii` (+16 байт на инстанс): `Params.x` занят радиусом, `.y` слотом трансформа,
   `.z` признаком чёткости — свободного места на три числа нет.

2. **Пунктир и обрезка при разных радиусах.** Заливка и СПЛОШНАЯ обводка получаются даром — они считаются из того же
   `d`. Пунктир и `trim` считают длину дуги, а при разных радиусах параметризация периметра другая: длина = сумма
   четырёх прямых участков и четырёх четвертей окружностей СВОИХ радиусов. Это выражается в замкнутой форме, то есть
   доводится до того же одного прохода, а не остаётся исключением. **Цель — чтобы отказ по пунктиру исчез совсем.**

3. **Дуги эллипса** — включить то, что уже написано (`TODO(arc)`), и разобраться с потерей устройства.

**Проверка:** сцена из несимметричных рамок, пунктирных рамок и колец прогресса рисуется одним-двумя instanced-draw, а
не сотней по-юнитных; снимок совпадает с по-юнитным путём попиксельно.

#### Каких примитивов не хватает, чтобы тесселяция осталась редким исключением

Формулы стандартные и замкнутые — десяток инструкций без ветвлений, точные, без приближений.

| примитив | чем закрывается | что перестаёт тесселироваться |
|---|---|---|
| **капсула** (отрезок с толщиной) | разделители, подчёркивания, линии сетки, соединители, линии графиков; **галочка чекбокса и шевроны складываются из 2-3 капсул** | обводка полилинии — сегодня полоса квадов с джойнами и капами, где у нас же живут шипы на miter'ах |
| **дуга / кольцо / сектор** | кольца прогресса, спиннеры, круговые слайдеры | шейдер клин УЖЕ умеет (`EllipseData.Arc`), включить батчинг |
| **треугольник, трапеция** | клювик подсказки, указатель выноски, вкладки в стиле Chrome, индикаторы сортировки | мелкие пути-иконки |

**Принцип важнее списка: сложную иконку дешевле сложить из трёх ИНСТАНСОВ, чем стесселировать один меш.** Инстанс уходит
в общий батч и почти ничего не стоит, меш — это машинерия на экземпляр. Поэтому цель — небольшой набор примитивов
(скруглённый прямоугольник с четырьмя радиусами, эллипс с дугой, капсула, треугольник), а не растущий зоопарк фигур.

#### Запекание MSDF для ПРОИЗВОЛЬНЫХ фигур — рассмотрено и ОТКЛОНЕНО

Идея была: произвольный `Path` → многоканальное поле расстояний, запечённое раз на идентичность (обе половины
механизма есть — `HaloFieldCache` печёт поля по `GeometryKey`, глифы уже рисуются MSDF) → один инстансный квад вместо
меша.

**Не делаем:** повторяющуюся стоимость уже снял кеш геометрии — произвольный путь тесселируется ОДИН раз на
идентичность и делится всеми экземплярами. Ради остатка заводить второй конвейер отрисовки — это параллельный механизм
при живом первом.

*Что кеш при этом не закрывает и о чём стоит знать:* меш печётся в локальном пространстве с фиксированной плотностью
вершин, поэтому при сильном увеличении на кривых проступает огранка, а поле расстояний осталось бы чётким. Вспоминать
об этом, только если это реально вылезет — например в редакторе с глубоким зумом.

### 4q. ГРАНУЛЯРНЫЙ отказ от патча — чинить СЕЙЧАС

**Замер (покадровый трейс, вкладка Layout, 15.08.2026):**

```
340 кадров  воспроизведение   0.09 мс
  1 кадр    полный обход     37.00 мс   why=патч отказал   by=TextRenderUnit
```

Разница в **четыреста раз**. И это не хвост распределения, а другой режим работы.

**Механизм.** `TryPartialReplay` идёт по грязным юнитам и **первый же** непатчируемый обрывает весь кадр:

```csharp
foreach (var u in g.Units)
    if (!IsSlotPatchable(u))
        return false;   // -> полный обход всей сцены
```

Не «этот нарисуем по-старому, остальные пропатчим», а «перерисовать всё».

**Почему это архитектурная дыра, а не медленный случай.** Оверлей диагностики не имеет к вкладке Layout никакого
отношения и ничего в ней не трогает — но его текст меняется 4 раза в секунду, и **каждый раз платит вся сцена**. Между
несвязанными поддеревьями возникает глобальная связность: стоимость кадра перестаёт быть функцией изменений и
становится функцией размера дерева. Это прямое нарушение инварианта §3, ради которого документ и заведён.

**Отказов на весь кадр не один, а ТРИ, и это разные механизмы.** Замер называл только первый; остальные видны в коде и
подтверждены с руки:

| # | вето | где | что роняет | замечено на |
|---|---|---|---|---|
| A | `!IsSlotPatchable(u)` у любого грязного юнита | `TryPartialReplay` | весь кадр | текст оверлея, `why=6 by=TextRenderUnit` |
| B | `LastBuildTransformDirty` — **что угодно сдвинулось где угодно** | вход в ОБА быстрых пути | весь кадр, ещё до разбора | переезд подсветки вкладки |
| C | `!group.PatchableRectOnly` / «юнит не `RectangleRenderUnit`» | `TrySplicedPatch` | весь кадр | смена числа юнитов у чего угодно нерект-ового |

**Чем это кончилось (замер, а не рассуждение).** B закрыто: сдвиг больше не отменяет записанный кадр. C сузилось до «не из одной арены» — вшивка работает со всеми семействами, а не только с прямоугольниками. A осталось как механизм, но перепись отказов на живой нагрузке показала, что **ни A, ни C туда не попадают**: 117 отказов из 471 попытки, и все — `arenaFull`, то есть переполнение арены, которое дробить нечем. Так что таблица описывает реальные механизмы, но приоритет из неё больше не следует — см. строку про гранулярный отказ в §7.

Вето B — самое злое из трёх: оно даже не смотрит, ЧТО сдвинулось. Одна анимированная подсветка вкладки = полный обход
сцены каждый её кадр.

**Что оказалось НЕ причиной — проверено в коде, а не по памяти.** Я записал было, что текст непатчируем из-за вершинного
буфера (`UsesStorageBuffer=false` у глифового батча) и что лечится это переводом глифов на хранилище. **Неверно, причём
дважды.** Во-первых, `UsesStorageBuffer` не переопределяет НИКТО — глифовый батч давно на BDA-хранилище и передаёт
`DrawBatch` адрес буфера; утверждение про вершинный буфер пришло из протухшего комментария в самом `BatchCollector`
(исправлен). Во-вторых, даже будь оно правдой, к патчу это отношения не имеет:
`UpdateSlot`, `FindSegmentContaining`, `ExcludeRun`, `AppendPatchSegment`, `PatchCapacityLeft` живут на ОБЩЕМ
`BatchCollector<TItem>` и работают через `Items[]` + догрузку диапазона — вид буфера им безразличен. Глифовый батч
умеет ровно то же, что и все прочие.

Настоящая причина в том, что **сам `RenderCache` рект-овый по построению**: `_rectSlotByUnit`/`_sdfSlotByUnit` заводятся
только для прямоугольников и эллипсов, `ControlGroup` описывает свой удержанный вклад одним полем `RectRuns` и одним
флагом `PatchableRectOnly`, а вся хирургия в `TrySplicedPatch` обращается буквально к `_rectBatch`. Остальные
одиннадцать коллекторов такого описания не имеют — не потому что не могут, а потому что им его не завели.

**Отсюда порядок работ (исправленный):**

1. **Описание удержанного вклада — ПО БАТЧУ, а не «ректы и всё».** ✅ *для перекраски* — `_sdfSlotByUnit` хранит
   «юнит → (вид, слот)» для ректов, градиентных ректов, эллипсов и градиентных эллипсов, `_textRunByUnit` — прогон
   глифовых слотов на юнит и атлас; `IsSlotPatchable`/`PatchSlot` знают все пять, `TextBatchCollector.UpdateRun`
   перепекает блок в занятые им слоты. Тем самым блок, у которого число глифов и атлас прежние (счётчик, часы,
   оверлей), патчится на месте вместо обхода сцены. Смена числа глифов пока честно отказывает — это случай хирургии
   сегмента, шаг 2. Осталось: сама **хирургия** так и работает по `_rectBatch` — `RectRuns` → прогоны на коллектор,
   `PatchableRectOnly` → «чем именно описан этот вклад», плюс описание для прочих коллекторов (инстансная заливка,
   паттерн, полосы). Ничего не ускоряет само по себе, но без этого хирургия остаётся рект-овой по построению, и
   «гранулярность» упрётся в тот же потолок.
2. **Гранулярное вето A и C.** Вместо `return false` на весь кадр — решение НА ГРУППУ: слот патчится на месте; менялось
   число элементов — хирургия сегмента (та же, что для ректов, теперь по своему батчу); не выходит ничего — перезаписать
   ЭТУ группу, а не сцену. Снимает класс: следующий неудобный тип кадр уже не обрушит.
3. **Вето B — отдельной работой, и оно рискованнее.** Слепой отказ «что-то сдвинулось» стоит там не зря: по-юнитная
   отрисовка запекает мировой трансформ в `RenderData` в момент ЗАПИСИ и слот-матрицу не читает, а батчи следуют за
   слотом ЖИВЬЁМ — на воспроизведении после сдвига половины кадра расходятся (замеренный разрыв в 48 px на прокрутке
   полосы вкладок). Механизм для лечения УЖЕ есть и уже работает: `ExecuteOps` перенацеливает по-юнитную отрисовку
   composited-владельцев (`op.Unit.Update(World(c), …)`). Работа — распространить его с composited-владельцев на любой
   сдвинувшийся узел движения, а слепое вето сузить до «сдвинулось то, за чем нечему следовать». **Тут нужен замер до и
   после, а не рассуждение** — комментарий в `ExecuteOps` прямо предупреждает, что зеркальная правка «перенацеливать
   всё» уже пробовалась и дала дрожание.
4. **Глифовый батч на хранилище — НЕ в этой работе.** Обоснование, под которым он сюда попал, оказалось ложным.
   Единственный оставшийся довод — однообразие пути per-instance (§4j), а это отдельный и необязательный пункт.

**Что стоит сделать ПЕРЕД шагом 2.** §0 уже требует починить расхождение порядка отрисовки с деревом (плавающий
`ViewportResize_Splices_…`, ровно 4 записи, подозреваемый — глобальный на все окна `RenderDirty`) прежде работ над
диапазонами. Шаг 2 — это ровно хирургия порядка: вставки в поток операций по месту. Строить её на основании, которое
раз в шесть прогонов уезжает на 4 записи, — значит потом не отличить свою ошибку от чужой.

**Проверка — тестом, а не глазами:** кадр, в котором ОДИН грязный юнит непатчируем, не должен перерисовывать остальные.
Считается по числу вызовов отрисовки у чистых юнитов: было O(сцены), стало O(грязного).

### 4o. ПОВТОРЫ: один объект, нарисованный N раз без N объектов — ✅ СДЕЛАНО

> Живёт в коде: `IUIComponent.RenderClones` (список матриц) + прогон клонов в обходе `RenderCache.Draw`; первый
> потребитель — `VirtualizingPanel.ReconcileSkeletons`. Клон получает свою матрицу и свой слот в `TransformTable`;
> элемента на карточку не существует. Ниже — обоснование и границы, они остаются в силе.
>
> **Известное ограничение, за которым тянется работа №6 из §7.** Клонированный юнит владеет слотом НА КАЖДЫЙ клон, а
> карта `_rectSlotByUnit` помнит один — последний записанный. Поэтому такой юнит исключён из БЫСТРОГО пути
> (`IsSlotPatchable` возвращает false).
>
> Работать это не мешает: перекраска идёт штатной дорогой
> `Brush.Opacity → RaiseChanged → InvalidatePaint → RenderDirty.MarkPaint` — компонент попадает в краска-грязные, его
> вклад перезаписывается вместе с прогоном клонов, и все карточки меняют цвет разом. `ApplyCompositedPaint` — это
> УСКОРЕНИЕ поверх неё (запись в слот на потоке рендера вместо перезаписи), и именно оно для клонов отключено. Цена:
> тик пульса перезаписывает вклад прототипа и заново выкладывает N инстансов вместо одной записи числа.
>
> Попытка срезать это патчем «весь прогон по группе» обошлась дорого и дважды: номера слотов перенумеровываются на
> КАЖДОМ обходе, набор клонов по ходу заполнения списка сокращается, и запомненный номер начинает принадлежать соседу —
> пульс перекрашивал первую звезду в такт с последней карточкой. Правильный ход — подключить альфу слота (§4m): тогда
> прозрачность перестанет быть поводом трогать инстансы вообще.

**Задача, из которой это выросло** (замер 15.08.2026): виртуализующая панель показывает скелетон-заглушку на каждый
незаполненный слот, и строит **полный экземпляр шаблона на слот** — 3469 сборок за четверть секунды при 147 реальных
контейнерах. Каждая сборка пишет свойства, каждая запись метит узел на пере-замер: `measure=15952 arrange=44949`.
Заглушка при этом одинаковая до пикселя.

**Ответ — не упрощать заглушку, а развернуть инстансинг в обратную сторону.**

Сегодня он идёт снизу вверх: **много настоящих объектов**, каждый даёт свою инстанс-запись, записи схлопываются по
идентичности геометрии. Нужен обратный ход: **ОДИН настоящий объект, чья инстанс-запись размножается N раз — меняется
только МАТРИЦА, всё остальное побайтовая копия оригинала.**

Из этого сразу следует, где работа: **не в дереве и не в панели, а в одном шве — там, где юнит запекается в
инстанс-запись.** Сегодня он выдаёт одну запись; надо научить выдавать N, подставляя матрицу. Новых понятий в дереве не
заводится, слоты `TransformTable` на клон не нужны — клон это строка в инстанс-буфере, а не узел.

Прототип при этом настоящий: построен по шаблону, измерен, расставлен, живёт в дереве — ровно один. Клоны существуют
**только в инстанс-буфере**.

**Почему это ложится на то, что уже построено:**

| нужно | чем закрыто |
|---|---|
| одна геометрия — много отрисовок | инстансинг по идентичности (`GeometryKey` + `InstancedFillCollector`): клоны одной рамки это ОДИН instanced-draw, трёх полосок — три, независимо от числа клонов |
| инстанс-запись, где меняется только матрица | она УЖЕ такая: `GeometryKey` намеренно исключает трансформ и цвет, они per-instance. То есть модель данных под клонирование готова, и менять её не надо |
| место в порядке отрисовки | весь набор клонов занимает ОДИН ранг: рисуются подряд, между ними ничего не вклинивается |
| анимация | клоны — копии записи прототипа, поэтому его анимация (общая пульсирующая кисть) видна во всех даром |

**Композиция матрицы, чтобы не ошибиться:** клон задаёт положение СЛОТА, а внутри поддерева у каждого юнита свой
локальный трансформ. Значит матрица клона не заменяет мировую, а **домножается**: `world = clone × local`. Иначе всё
поддерево схлопнется в точку слота.

#### Предельно дешёвая форма: ОДНА запись + диапазон матриц

Копировать инстанс-запись N раз — уже лишняя работа: каждый кадр это N × размер_записи байт на ЦПУ, хотя меняется
только матрица. Предел такой:

- **одна** инстанс-запись прототипа;
- **диапазон слотов** в `TransformTable` — по слоту на клон;
- отрисовка с `instanceCount = N`, шейдер берёт матрицу как `table[slotBase + gl_InstanceIndex]`, где `slotBase` —
  константа на вызов.

**Работы на ЦПУ на клон не остаётся вообще** — только сами матрицы, и только когда они изменились. `TransformTable` уже
устроена ровно так: матрицы в GPU-буфере, доступ по индексу через BDA, копия на кадр в полёте, ленивый догон — на
неподвижном кадре ноль байт.

**И путь данных под это УЖЕ такой, какой нужен** (проверено в `BatchEffect.fx`, 15.08.2026):

```hlsl
PSInput RectBatchInstancedVS(uint vertexId : SV_VertexID, uint instanceId : SV_InstanceID)
{
    RectData* items = (RectData*)InstancesAddress;   // BDA-буфер, НЕ вершинный ввод
    RectData item = items[instanceId];
    float4x4* transforms = (float4x4*)TransformsAddress;
    float4x4 nodeWorld = transforms[(uint)item.Params.y];   // слот трансформа — ПОЛЕ записи
```

Вершинного ввода у этого прохода нет вовсе: квад берётся из `SV_VertexID`, запись — из буфера по `SV_InstanceID`.
`BatchCollector.UsesStorageBuffer` по умолчанию `true`; вершинными атрибутами остался только глифовый батч.

**Значит предельная форма достижима сразу, без промежуточной ступени.** Нужна одна маленькая правка шейдера: режим, в
котором индекс записи фиксирован, а слот берётся со сдвигом —

```hlsl
RectData item = items[cloneBase];                  // одна запись на весь набор
float4x4 nodeWorld = transforms[(uint)item.Params.y + instanceId];   // слот = база + номер клона
```

Запись уже несёт базовый слот в `Params.y`, так что шейдеру достаточно прибавить номер инстанса. На ЦПУ на клон не
тратится **ничего**: только матрица в `TransformTable`, и только когда она изменилась.

**Единственная цена:** такому набору нужен СВОЙ вызов отрисовки — адресация матрицы у него другая, в общий батч с чужой
геометрией он не сольётся. Один лишний draw на весь набор клонов; за тысячи заглушек это ничто.

**Форма API — минимальная, без новых понятий в дереве:** у компонента есть список повторов (`RenderClones`, матрицы), по
умолчанию пустой. Кеш умножает вклад компонента на этот список. Панель ставит его прототипу — и всё; никакого особого
режима у панели не заводится.

**Что клоны немедленно потребовали.** Клон живёт в СВОЁМ слоте таблицы трансформов (иначе все клоны схлопываются туда,
куда легла последняя запись — проверено на живом стенде). Значит индекс на клон уже есть, и альфа по тому же индексу
даёт прозрачность НА КЛОН — поле в слоте под неё готово и шейдер её читает, не подключён только источник (§4m). Пока
источника нет, пульс общей кисти вынужден идти через перекрас слотов, а для клонов он вовсе запрещён — см. ограничение
в начале раздела и работу №6 в §7.

**Границы, которые надо назвать вслух, потому что они и делают это дешёвым:**

- **Повтор НЕ интерактивен.** Его нет ни в визуальном, ни в логическом дереве: не попадает под курсор, не получает
  фокус, не имеет своего состояния. Всё, с чем взаимодействуют, обязано быть настоящим объектом. Для заглушки это не
  ограничение, а ровно то, что нужно (`IsHitTestVisible="False"` там и так стоит).
- **Все повторы одинаковы.** Отличается только трансформ. Различный текст на повторах невозможен — и именно поэтому
  это дёшево. (Цвет на инстанс модель уже умеет, так что оттенок на повтор — естественное расширение, но обещать его
  сейчас не будем.)
- **Прототип должен быть расставлен в тот же размер**, что и слоты. Для равномерной сетки это так по построению;
  для разноразмерных слотов масштаб в трансформе растянет и обводку — значит там повторы не применимы.

**Что это даёт помимо скелетонов:** повторяющиеся украшения, призрак при перетаскивании, предпросмотр, любая сетка
одинакового. То есть панель перестаёт быть особенным случаем, а способность становится общей.

**Где риск оказался на деле:** не в порядке отрисовки — прогон встаёт на место группы-хозяина и наследует её ранг, — а в
том, что «юнит ↔ слот» перестало быть один-к-одному. Всё, что читало эту связь как единственный слот, начало промахиваться
мимо чужих элементов. Отсюда ограничение выше и работа №6.

### 4l. Настоящая глубина и граница 3D-прохода

Порядок отрисовки задаётся положением в списке (ранги с зазорами, §4b) — глубины у нас нет и буфер глубины выключен.
Соблазн выдать каждому элементу реальный Z по месту в обходе и отдать сортировку буферу глубины **как замену порядку не
работает**: UI почти весь на альфа-смешивании, а аналитическое сглаживание даёт полупрозрачную каёмку — такое обязано
рисоваться сзади вперёд. Настоящая цена корректности здесь — OIT (weighted-blended, depth peeling, списки на пиксель),
отдельная подсистема.

Но у настоящей глубины есть своя причина существовать, и она не про оптимизацию: **пока контролы компланарны, порядок
обхода — исчерпывающий ответ; как только контрол получает настоящий 3D-трансформ, компланарность кончается**,
геометрия может пересекаться, и порядок обхода перестаёт быть правдой физически. Это прямо по вижну движка (UI внутри
3D), так что вопрос не «надо ли», а «где граница».

Предлагаемая граница: **плоская 2D-сцена живёт порядком и глубины не знает; узел, ЯВНО объявивший 3D-трансформ,
становится границей 3D-прохода** — внутри него глубина, тест и своя политика прозрачности. Так это устроено в браузерах
(`transform-style: preserve-3d` + контексты наложения), и там же видно, во что обходится непроведённая граница.

**Открыто:** что происходит с 2D-содержимым ВНУТРИ повёрнутого узла — запекается в цель и кладётся текстурой (просто,
текст мылится) или рисуется прямо в 3D с перспективным трансформом (чётко, но каёмка и глифы должны это уметь).

### 4m. Иерархия узлов — ⚠️ НАПОЛОВИНУ УЖЕ ЕСТЬ, строить надо не с нуля

> **Сверено с кодом и с `TECH_DEBT.md` 15.08.2026.** Ниже описывалось как замысел то, что для ТРАНСФОРМА уже
> реализовано в `Rendering/TransformTable`: узлы движения (редкие, с пулингом слотов), индекс слота на инстансе,
> шейдер достаёт матрицу по индексу через BDA, сдвиг поддерева = одна запись. Значит новую иерархию заводить НЕЛЬЗЯ —
> будет параллельный механизм. Расширять надо ту.

**Что уже есть (`TransformTable`):**
- узел = элемент, чьё поддерево движется самостоятельно (прокручиваемая панель, анимируемая плитка) — те самые
  «редкие узлы»;
- покоящийся элемент **делит слот ближайшего предка-узла**, а начав двигаться сам — повышается в свой и отпускает,
  закончив. Это и есть наследование, выраженное пулингом;
- копия таблицы на кадр в полёте, догоняется лениво: изменившиеся слоты, на неподвижном кадре ноль байт.

**Альфа на узел УЖЕ ЕСТЬ в той же таблице** — и не как замысел: слот несёт `Params.x` рядом с матрицей, есть
`TransformTable.SetAlpha`, шейдер читает её живьём (`float slotAlpha = nodes[...].Params.x`). Не хватает только
ПОТРЕБИТЕЛЯ: `SetAlpha` в UI не вызывает никто, element-`Opacity` до сих пор запекается по-юнитно. То есть работа
здесь — подключение, а не постройка.

**Чего не хватает — два расширения ТОЙ ЖЕ таблицы, а не новая структура:**

| что | как | закрывает долг |
|---|---|---|
| **отцепление/возврат поддерева** по узлу вместо метки на каждый компонент | узел знает свой диапазон | замеренные 12 мс на 5900 узлов |
| **отсев по узлу** | рамка узла → пропуск диапазона | ничего в долге, наша хотелка |

**Чего эта иерархия НЕ закрывает — важно не обмануться:**

- **Групповая непрозрачность останется НЕВЕРНОЙ.** Каскад даёт дешёвое *применение* альфы, но при `Opacity < 1` дети,
  перекрывающие друг друга, всё равно смешиваются дважды — нужен настоящий слой (`LayerOpacity`, offscreen).
  `TECH_DEBT` → Opacity → «`LayerOpacity` / offscreen-слой», `OPACITY_MODEL_PLAN.md` §3. Умножение альфы на инстанс
  этого не чинит **никак**.
- **Скруглённое отсечение** остаётся отдельной задачей: узел может нести клип, но `ClipToBounds` не знает про
  `CornerRadius` — нужен попиксельный клип в SDF-шейдерах или маска. `TECH_DEBT` → Рендер/GPU. Та же инфраструктура,
  что у `LayerOpacity`.

**Предупреждение из долга, прямо относящееся к диапазонам:** `ViewportResize_Splices_AndKeepsDrawnGeometryFresh`
плавает — «the spliced paint order drifted from the tree's», расхождение всегда ровно на 4 записи, зависит от порядка
и от того, что `RenderDirty` — ГЛОБАЛЬНОЕ множество на все окна. То есть инвариант «порядок отрисовки соответствует
дереву» **уже нарушается время от времени**, до всяких диапазонов. Чинить это надо ДО того, как на порядок ляжет ещё
и разметка поддеревьев, иначе новый механизм будет строиться на плывущем основании.

**Ещё ограничение из долга:** параллельный бейк (`TECH_DEBT` → Рендер/GPU) не сделан, крукс — потокобезопасность
записи юнитов и слотов. Любая перестройка обязана его не закрыть окончательно.

#### Что осталось спроектировать

Каскад трансформа готов (`TransformTable`), поэтому проектировать надо только то, чего таблица слотов пока не умеет —
**операции над поддеревом как над целым**. Для этого узлу нужен его ДИАПАЗОН.

- **Диапазон узла** — поддерево в списке отрисовки непрерывно: `[start, start + subtreeCount)`. `subtreeCount`
  обновляется по цепочке предков при структурном изменении, это O(глубины).
- **Отцепить поддерево** — пометить диапазон неактивным. Юниты не трогаются, обхода нет. Вернуть — обратное; значения
  на узлах те же, если мир не изменился (сторож — как у парковки вьюх).
- **Отсев** — рамка узла не пересекается с областью → пропуск всего диапазона.

**Риски, и оба не теоретические:**

- **Ошибка в диапазоне портит порядок отрисовки МОЛЧА.** Сторож обязателен и не опционален: диапазон узла обязан
  совпадать с его фактическим поддеревом, проверяется в отладке на каждом структурном изменении. Тем более что
  расхождение порядка с деревом у нас уже наблюдается (плавающий `ViewportResize_Splices_...`).
- **Вставка в середину** сдвигает индексы у всех, кто дальше. Лечится тем же, чем уже лечится порядок — зазорами, —
  либо косвенным слоем «слот → индекс». Решать замером при реализации.
- **Узел не должен становиться зеркалом компонента** (§3a). Правило: узел заводит тот, кто просит каскад или
  отцепление, и он же его снимает. `TransformTable` уже так и работает — слот берётся при начале самостоятельного
  движения и отпускается по окончании.

#### Чего иерархия не решает — чтобы не было иллюзий

| проблема | решается чем |
|---|---|
| ×3-4 компонента на логический айтем | схлопывание (§4c), и оно само под вопросом |
| **прокрутка 60k тормозит в РАСКЛАДКЕ** | не рендер вообще; замерено, причина в layout |
| обход прицепления в 5900 узлов на стороне UI | ревизия жизненного цикла компонентов, не рендера |
| групповая непрозрачность двоит альфу на пересечениях детей | настоящий слой (`LayerOpacity`), каскад тут бессилен |
| скруглённое отсечение | попиксельный клип в SDF-шейдерах или маска |

Иерархия убирает обход по **рендер-юнитам**; обход по **компонентам** при прицеплении останется — это разные деревья.

### 5a. Направление: КОРЗИНЫ РАНГА вместо одной линейной арены

Три разных бага этой недели имеют один корень — **всё лежит в одной линейной арене, а место в ней задано порядком
обхода**: пульс скелетона перекрашивал перенумерованный слот, слот трансформа доставался чужому элементу, новичок при
сплайсе рисовался под чужой карточкой. Каждый чинился отдельно; общая причина осталась.

Предложение — сделать структуру **слоистой**: не один поток, а массив плоских арен, и порядок задан индексом, а не
позицией в потоке. Тогда появление контрола не перенумеровывает ничего за пределами своей арены, вставка = «дописать в
конец своей», а разрезы сегментов (§4m) становятся ненужными.

**Что такое слой.** Множество отрисовок, внутри которого порядок БЕЗРАЗЛИЧЕН, а всё остальное рисуется строго раньше
или строго позже. Ключевое: это НЕ уровень иерархии. Глубина порядка не задаёт (глубокий ребёнок раннего сиблинга
рисуется РАНЬШЕ мелкого позднего), и два сиблинга одной глубины могут перекрываться — тогда их порядок важен и в один
слой они не идут. Место слоя в порядке описывается **интервалом рангов**, а не точкой.

**Главное наблюдение: эти слои у нас уже есть.** Кэш вычисляет их на каждом обходе — сегмент сбрасывается, когда
следующий юнит ПЕРЕКРЫВАЕТСЯ с накопленным (`BatchCollector.OverlapsPending`: «позже и перекрывается ⇒ после сброса;
пространственно раздельные, как строки списка, — нет»). То есть нынешний сегмент И ЕСТЬ слой в этом смысле. Беды две, и
обе про то, что слой не первоклассен:

1. классы **вычисляются заново** каждым обходом и склеиваются в ОДНУ линейную арену — отсюда перенумерация слотов и
   патчи не по адресу;
2. место слоя записано **точкой** (один ранг) вместо интервала — отсюда сегодняшний дефект порядка (§7) и разрез как
   его починка.

**Отсюда — во что превращается работа.** Не «завести слои», а сделать существующие классы устойчивыми: у слоя своя
арена и свой интервал рангов; вставка = найти слой по рангу и дописать; новичок перекрывается с содержимым — открыть
новый слой сразу за ним (та же операция, что сейчас делает `SplitSegmentSpanningRank`, но как штатная, а не как
починка). Разрезы и перенумерация исчезают вместе с общей ареной.

**Про число вызовов.** Оно НЕ вырастет: слоёв столько же, сколько сегментов сегодня, потому что правило слияния то же
самое (перекрытие). Вырастет оно только если ключом сделать глубину — тогда глубокий интерфейс дробится на тонкие слои,
а то, что можно было слить, не сливается. Поэтому замер ДО реализации нужен ровно один: сколько слоёв даёт живое окно
(вкладка Layout, риббон) при выбранном ключе и во сколько вызовов это превращается против нынешних. Если число совпало с
числом сегментов — ключ выбран верно.

разложена по сценам (пункт 5 выше), и работы по диапазонам поддеревьев лягут уже на это основание.

**Что этот заход сказал про метод, а не про код.** Оба живых бага дня искались часами и оба нашлись, когда я перестал

сначала правка «по похожести», потом проверка — за вечер дал три правки в верные, но ПОСТОРОННИЕ места.

## 6. Не-цели сейчас / отдельные треки
- **Внутрикадровая MT-запись команд — НЕ-цель** (по правильной причине): инстансинг + retained сводят запись к горстке instanced-draw (µs), чистый кадр не пишет ничего → распараллеливать нечего; MT добавил бы sync-оверхед и недетерминизм против снапшот-тестов. Пересмотр — только если замер на 100k+ сцене покажет однопоточный МЕРДЖ/тесселяцию пределом (и тогда параллелим ИХ, не запись).
- **Per-window parallelism — легитимный ОТДЕЛЬНЫЙ трек (после retained-редизайна).** Окна уже независимые юниты (свой кэш/swapchain) → оркестрация, не переписка внутренностей. Нюансы: (1) retained-редизайн сам чинит общий случай — простаивающее окно стоит ~0 (пере-present), платим только за активные; (2) MT добивает остаток «много окон активны разом» = max(окон) вместо sum; (3) осуществимость зависит от модели девайса (`CreateRenderDevice` пер-оконный vs общий → тривиально vs нужен thread-safe heap/pools); (4) `vkQueueSubmit`/present не thread-safe → запись параллельно, submit серийным хвостом. Включаем под измеренную нужду «много одновременно активных окон».
- Смена modern-pipeline решений Vulkan (shader objects / dynamic rendering / descriptor buffer/heap остаются).

## 10. Прокрутка: что измерено 2026-08-25 и чего это стоило по ошибкам

### Метрика, по которой надо судить

**`loopMs` не предсказывает фриз.** Средний fps по корзинам `loopMs`: 0-49 → 415, 50-99 → 237, 100-149 → 181,
150-199 → 112, а дальше **обратно вверх**: 200-249 → 336, 250-299 → 387, 300-349 → 380. Секунды с `loopMs` 241-316,
из-за которых поднималась тревога, шли на 319-480 fps, то есть невидимы: компоновщик презентует независимо от потока
цикла, длинный кадр цикла картинку не морозит.

**Предсказывает `gcPause`**, монотонно и без исключений:

| пауза сборщика, мс/с | секунд | fps min | **fps средний** | fps max |
|---|---|---|---|---|
| 0-49 | 636 | 63 | **413** | 900 |
| 50-99 | 17 | 85 | 353 | 568 |
| 100-149 | 17 | 85 | 265 | 499 |
| 150-199 | 17 | 16 | 189 | 480 |
| 200-249 | 5 | 14 | 163 | 380 |
| 250-299 | 3 | 11 | **64** | 160 |

Отсюда единственный рычаг на то, что видно, — **темп выделения памяти**. Опорные числа на секундах построения
вкладки: **46-170 МБ/с**, из них раскладка (`layMB`) **21-91 МБ — около половины**; худшие секунды (170 и 157 МБ)
дали gc 267-287 мс и **fps 23 и 11**.

### Четыре ошибки этого разбора — чтобы не повторять

1. **`loopMs` объявлен показателем фриза.** См. выше: выше 200 мс связь с fps обратная.
2. **«Куча растёт монотонно, значит удержание».** `heapMB` — это `GC.GetTotalMemory(false)`, БЕЗ принудительной
   сборки: в неё входит неубранный мусор. Вывода про удержание оттуда не следует. И это не то же, что показывает
   диспетчер задач (рабочий набор процесса, вместе с нативной памятью и GPU).
3. **Молчание счётчика прочитано как значение.** `RecyclePoolSize` присваивался ТОЛЬКО внутри `ReclaimDetached`;
   тот не вызывался ни разу, поле осталось нулевым, и я объявил «пул пуст». После переноса замера на путь, который
   отрабатывает всегда (`SetWindow`), пул оказался до **4725**. Диагностика, чьё молчание неотличимо от значения,
   хуже отсутствующей.
4. **Завышенный прогноз выигрыша.** Я сказал «`arrLoopMs` — это 20-45% расстановки, и это накладные расходы цикла».
   Неверно: `arrLoopMs` всегда включал и НАСТОЯЩУЮ работу — расстановку въехавшего ряда. Убрана только холостая часть.
   Видно по цене посещения: было 1,3 мкс, стало 4,5-23 мкс — не потому что хуже, а потому что дешёвые холостые
   посещения исчезли и остались работающие. `layArr` упал на 0-25%, а не на 20-45%.

### Гипотеза, проверенная и отклонённая

«Числа испортил мой же счётчик инвалидаций (`ADAM_LAYOUT_COUNT`)» — прогон без него дал на той же вкладке
(`att=3583`) `loopMs` **290 и 316** против 241 и 249 со счётчиком. Прибор себя не мерил.

### Что осталось открытым здесь

- **Темп выделения памяти** — единственное, что двигает `gcPause`, а значит и fps. Половина приходится на раскладку.
- **Остаток `layArr`** (примерно 40-110 мс/с) после снятия холостых обходов: `ArrangeCore` изменившихся плиток плюс
  `AnimateLayoutMoves`, `ReconcileDropPlaceholder`, `ReconcileSkeletons`. Не разложен.

### Счётчик виновников: кто на самом деле грязнит замер при прокрутке

Прогон 25.08.2026 с `ADAM_LAYOUT_COUNT=1`, самая занятая секунда — **331 821 инвалидация**, 31 проход раскладки,
32 вызова `SetWindow`:

| причина | за секунду | на один `SetWindow` |
|---|---|---|
| **`ItemContainerGenerator.*deferred*`** | **143 585** | **4 487** |
| `ListBoxItem.*any-measure*` | 18 277 | 571 |
| `*unmapped*` (ушли из окна) | 14 043 | 439 |
| `*rebound*` (реально привязано) | 11 440 | **357** |
| `ContentPresenter.Content` / `ListBoxItem.Content` | по 11 440 | 357 |
| `ListBoxItem.Visibility` | 6 837 | 214 |

**Первый вывод — замеры ЧЕСТНЫЕ.** 357 привязок × 2 компонента ≈ 714 замеров на проход, а посекундный лог давал
500-750. Сходится в упор: замер при прокрутке — это не грязь и не каскад, это внутренняя раскладка плиток, которым
дали новое содержимое. Поэтому пункт «замер дороже расстановки втрое-вчетверо» **снят из `TECH_DEBT`**: это не
дефект, это цена работы. Вопрос, если возвращаться, звучит иначе — «почему один замер плитки стоит ~20 мкс».

**Второй вывод — размазывание.** За проход из окна уходит 439 плиток, бюджет в 6 мс успевает привязать 357, а
**4 487 слотов откладываются** и получают скелетоны; следующий проход — снова. Плюс `park` 402-6020 вызовов в
секунду, а каждый `ParkContainer` рекурсивно гасит привязки во всём поддереве — отсюда и 6 837 записей `Visibility`.

**Чем кончилось.** Первым побуждением было бюджет снять — и это была ошибка, см. границу решения в §0: снятие меняет
размазывание на жёсткий фриз. Проверено ползунком на живом стенде: **при `0` фризы прокрутки заметны глазом, с
бюджетом лучше.** Бюджет вынесен настройкой (`ScrollBindBudget` / `FillBindBudget` / `MinBindsPerPass`, `0` = нет),
потому что правильного значения на все окна не существует: на большом окне при минимальной ячейке размазывание
объективно предпочтительнее, на маленьком — наоборот.

### Коллекции ради одного вызова: обойдено, паттерн исчерпан

Пункт закрыт 2026-08-26. Искали «массивы и списки, живущие ровно один вызов» — нашли ровно одно место с реальной
частотой и одно ложное направление.

**Путь применения стилей — было и вылечено.** Он отрабатывает на каждый компонент при построении и перетемизации:
`AttachStyles`/`DetachStyles`/`Style.Apply`/`UnApply`/`ApplyExternalStyles` принимали `params Style[]` (массив на
вызов, включая массив из ОДНОГО элемента внутри цикла отцепления), плюс два `ToArray()` в `ApplyCurrentThemeAndStyles`.
Переведено на `params ReadOnlySpan<Style>`; защитная копия `_attachedStyles.ToArray()` заменена обходом по индексу
НАЗАД (удаление сдвигает только пройденное); у `AdamantiumCollection<T>` появился `AsSpan()`.

**Замерено:** `params ReadOnlySpan` — **0,0 байт на вызов** против **40,0** у `params T[]` (утверждение в зонде, а не
рассуждение: `params` со span-типом — это C# 13, элементы живут во встроенном массиве на СТЕКЕ, а не в куче).
На настоящем пути: прицепление+отцепление двух стилей **704 Б/компонент со спанами против 768 с массивами, экономия
64**, плюс ~80 на перетемизации. То есть **64-144 байта на компонент** — честно, но рядом с −2176 от §11 это мелочь.

**Ложное направление — «и в командах отрисовки».** В `IDrawingSession`/`IDrawingContext` **нет ни одного параметра-
коллекции**. Замер перетаскивания: 1661 КБ/кадр, из них 1381 в `render` — и это **два объекта на команду**
(`RectanglePayload` ~112 Б, `DrawCommand` ~56 Б, ~6000 отрисовок за кадр). Задача настоящая и на порядок крупнее, но
другого рода: пул команд или полезная нагрузка структурой.

**Проверено и признано не при чём:** `PushChildrenInPaintOrder` уже имеет безаллокационный путь по индексу
(`Reverse()` только в запасной ветке); сортировка по `ZIndex` срабатывает лишь при ненулевом `ZIndex`; `CopyCommands`
— массив на компонент, но только на полном обходе; ввод, фокус и навигация выделяют списки на человеческой частоте.

**Осталось незамеренным:** маршрутизируемые события — `handlersList.ToArray()` на КАЖДОЕ возбуждение (нужна как
защита от подписки/отписки внутри обработчика, но делается всегда, включая случай одного обработчика) и
`GetTunnelEventRoute()` = `GetBubbleEventRoute().Reverse()`, буферизующий весь маршрут. Частота не измерена — браться
только после замера.

### Параллельный бейк — ОТКЛОНЁН 2026-08-26, не предлагать снова

Расстановка распараллелена (`StackPanel`/`WrapPanel`), запись юнитов и слотов — нет: `Parallel.` не встречается в
`Adamantium.UI/Rendering` ни разу. Это верно, и так и останется. Пункт удалён из `TECH_DEBT` не как сделанный, а как
**отвергнутый**, по двум причинам сразу.

**Выигрыша почти нет.** Замер перетаскивания на 4К, на кадр: раскладка 12,5 мс, **запись 29,8**, **бейк 10,1** —
бейк самая МАЛЕНЬКАЯ из трёх фаз, ~19% кадра, и часть его это запись в буферы GPU, которую драйвер всё равно
сериализует. Плюс к этому §10: видимую просадку определяет `gcPause`, а не время кадра, и крупнейшее выделение
сидит в `render` (1381 КБ из 1661), не в бейке. То есть работа целилась бы в третью по величине фазу мимо того,
что реально видно.

**Риск в самом дорогом классе ошибок.** Порядок отрисовки И ЕСТЬ порядок списка групп, и он строится
последовательными вставками по ходу обхода (`_groups.Insert(FirstGroupAfter(order), …)`, `_groups.Add(…)`). Печь
параллельно — значит требовать, чтобы каждая группа сама знала своё итоговое место, плюс детерминированный слив.
Выполнимо, но это ровно те грабли, на которые здесь уже наступали: вшивка не на том ранге, `SplitSegmentSpanningRank`,
фантомные плитки. Сверх того бейк трогает общее изменяемое состояние — арены, атласы глифов, буферы.
