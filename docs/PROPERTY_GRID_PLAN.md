# PropertyGrid — проект

Инспектор свойств вроде того, что в Visual Studio: слева имя, справа редактор, посередине перетаскиваемый
разделитель. Первый потребитель — правка компонентов ECS-сущности в редакторе.

Документ фиксирует решения до кода. Реализация — отдельной работой.

## Что это и чем НЕ является

Это **не таблица с двумя колонками**. Похоже снаружи, но внутри другое:

- В таблице тип задаёт **колонка**, и он один на весь столбец. Здесь тип задаёт **строка**: `Position` — три числа,
  `IsEnabled` — флажок, `Material` — выпадающий список, и всё это в одном столбце подряд.
- В таблице строки однородны и виртуализуются арифметикой. Здесь строки разной высоты и вложены друг в друга
  (`Transform` раскрывается в `Position`/`Rotation`/`Scale`).
- Таблица показывает МНОГО строк одного вида. Инспектор — ДЕСЯТКИ строк разного вида.

Поэтому это отдельный контрол, а не режим `TreeDataGrid`. Общее у них — иерархия строк (тот же `TreeFlattener`) и
перетаскиваемый разделитель; их и переиспользуем.

## Строка = тип, как колонка в таблице

Ровно та же схема, что уже доказала себя в `DataGridColumn`: базовый тип объявляет, что умеет строка, наследники
приносят свой редактор.

```
PropertyRow (abstract)
├── Name / Description / IsReadOnly / Category
├── ValueTemplate        — как значение ВЫГЛЯДИТ, когда его не правят
├── EditorTemplate       — во что превращается при правке
├── PrepareEditor(editor, value) / ReadEditor(editor)
└── EditsOnClick         — флажку двойной клик не нужен

├── StringPropertyRow    — TextBox
├── NumericPropertyRow   — NumericUpDown; Minimum/Maximum/Step/Decimals; поддержка drag-scrub (он уже есть)
├── BooleanPropertyRow   — CheckBox, правится одним кликом
├── EnumPropertyRow      — DropDown, значения из типа перечисления
├── ChoicePropertyRow    — DropDown по списку, который даёт провайдер (материалы, меши, слои)
└── CompositePropertyRow — узел: сам не правится, раскрывается в дочерние строки (Vector3 → X/Y/Z)
```

Первая итерация — строка, число, флажок, выпадающий список; `Composite` нужен сразу, иначе `Vector3` не показать.

## Откуда берутся строки

Три источника, и это ВАЖНОЕ решение — контрол не должен знать про рефлексию:

1. **Явно, из разметки** — `<StringPropertyRow Header="Name" Path="Name"/>`. Полный контроль, нужен для
   инспекторов, которые рисуются вручную.
2. **От провайдера** — `IPropertySource`, по образцу `IDataGridCells`: `GetRows(object target)`,
   `GetValue`, `TrySetValue`, `IsReadOnly`, `ChoicesFor`, `Changed`. Вью-модель редактора решает, что показать
   про компонент, и не отдаёт контролу ни рефлексию, ни кисти.
3. **Автоматически по типу** — `PropertyRowBuilder`: рефлексия по публичным свойствам, тип → тип строки,
   `[Category]`/`[DisplayName]`/`[Browsable]`/`[Range]` учитываются. Живёт **отдельным классом**, а не внутри
   контрола: инспектор без рефлексии должен собираться.

Для ECS работает третий путь: `EntityComponentCollection` даёт `IComponent`, каждый компонент — категория,
его свойства — строки.

## Разделитель

Одна вертикальная линия на весь контрол, тянется мышью, курсор `SizeEWE`. Позиция — `NameColumnWidth`
(bindable, доля или пиксели), с минимумами с обеих сторон. Это ровно то, что уже сделано в
`DataGridHeadersPresenter` для колонок; берём оттуда, а не пишем заново.

**Важно:** разделитель общий для ВСЕХ строк, включая вложенные. Иначе вложенные значения не выстроятся в столбец,
и инспектор развалится на лесенку.

## Секции — и `Expander`, которого в движке нет

Инспектор делится на **секции с заголовком, которые сворачиваются**: `Transform`, `Rendering`, `Physics`. В ECS
это ровно один компонент = одна секция, и иначе быть не может — свойства двух компонентов нельзя показывать
вперемешку.

Проверено: **контрола `Expander` в движке нет.** Есть только глифы-раскрывашки внутри шаблонов `TreeView` и
`TreeDataGrid` — то есть каждый контрол рисует свою. Значит, `Expander` пишется как **самостоятельный контрол**, а
не как часть инспектора: он нужен всему остальному тоже (страницы настроек, панели инструментов, группы в
диалогах), и заводить его внутри `PropertyGrid` — значит через месяц писать второй такой же.

```
Expander : ContentControl
├── Header / HeaderTemplate      — заголовок; шаблон, потому что там бывает не только текст
├── IsExpanded (bindable)
├── ExpandDirection              — Down по умолчанию; Up/Left/Right для панелей
├── Expanded / Collapsed         — события
└── PART_Header (нажимается целиком, не только глиф), PART_Glyph, PART_Content
```

Свёрнутый экспандер **не меряет** своё содержимое (`Visibility.Collapsed`), иначе список из тридцати свёрнутых
секций всё равно построит все тридцать наборов строк. Здесь придётся помнить про уже известную ловушку:
схлопнутое поддерево не участвует в замере, и элементы внутри него надо будить явно при раскрытии.

### Как секции устроены в самом инспекторе

`PropertyGrid` — это список **секций**, каждая секция — `Expander`, содержимое которого — набор строк. Не один
плоский список с category-строками внутри, и вот почему: у секции есть настоящая шапка со своим оформлением,
своим состоянием и своим контекстным меню, а строка-заголовок внутри плоского списка всё это будет изображать.

Следствия, которые принимаем сознательно:

- **Разделитель — общий на весь контрол**, а не на секцию. `NameColumnWidth` живёт в `PropertyGrid`, секции его
  только читают. Иначе колонки в разных секциях разъедутся, и инспектор развалится на лесенку.
- **Виртуализация — внутри секции, а не поверх всех.** Секция инспектора — это десятки строк, не тысячи; первой
  итерации виртуализация не нужна вовсе. Если у компонента когда-нибудь окажется двести свойств, виртуализуется
  панель строк этой секции, и контракт для этого уже есть.
- **Раскрытость секции хранит вью-модель**, а не контрол: выбрали другую сущность — секции должны остаться
  такими, какими их оставил пользователь.

## Категории и раскрытие

- Композитное свойство (`Transform` → `Position`/`Rotation`/`Scale`) — узел ВНУТРИ секции; отступ по глубине, как
  в `TreeDataGrid`. Его раскрывашка — та же, что у дерева, а не экспандер: это строка, а не секция.
- Порядок: секции в объявленном порядке, внутри — свойства в порядке источника (НЕ по алфавиту:
  `X`, `Y`, `Z` важнее алфавита). Сортировка по имени — переключатель, как в VS.

## Множественный выбор

Инспектор в редакторе почти всегда правит НЕСКОЛЬКО выделенных сущностей. Это закладывается в контракт с самого
начала, иначе потом придётся переписывать всё:

- `SelectedObjects` (не `SelectedObject`), строки — пересечение свойств по всем объектам.
- Значения различаются → строка показывает пустое поле с признаком «разные», правка применяется ко всем.

## Правка

Механика уже написана и проверена в `TreeDataGrid` — берём её целиком:

- Двойной клик / `F2` — начать; `Enter` — записать; `Escape` — отменить; уход фокуса — записать.
- Флажок и выпадающий список правятся ОДНИМ действием (`EditsOnClick`), выпадающий завершает правку по выбору.
- Запись идёт через источник (`TrySetValue`), а не мимо него.
- Отказ на уровне свойства (`IsReadOnly`) и на уровне значения (валидация: неверное значение оставляет строку в
  правке и подсвечивает её).

## Что решаем позже

- **Кнопка «…»** у строки — диалог выбора (цвет, файл, ссылка на ассет). Дизайн после первой итерации.
- **Сброс к значению по умолчанию** — жирная точка/стрелка справа, как в Unity.
- **Поиск по свойствам** — поле над списком, фильтрует строки; на существующей машинерии фильтра это дёшево.
- **Анимационные ключи** — привязка строки к дорожке анимации.

## Порядок работ

0. **`Expander`** — самостоятельный контрол, со своими темами и тестами. Без него секций не будет.
1. `PropertyRow` + четыре типа строк + `CompositePropertyRow`, ручное объявление в разметке.
2. Разделитель, секции на `Expander`, раскрытие, темы (macOS / Fluent / Editor Pro).
3. `IPropertySource` и правка через него.
4. `PropertyRowBuilder` (рефлексия) и мост к ECS.
5. Множественный выбор.
