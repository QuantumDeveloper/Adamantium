# Технический долг Adamantium.UI — что недоделано

_Только открытое. Закрытое отсюда удаляется: разбор закрытых заходов живёт в планах (`docs/*_PLAN.md`) и в истории коммитов. Перед тем как брать пункт — сверь с кодом, заметки протухают._

Приоритеты: **P1** мешает уже сейчас · **P2** нужно для качества/перфа · **P3** будущее/дизайн.

---

## Opacity

- **[P2] Прозрачность НА КЛОН невозможна.** Клоны делят слот прототипа (`OpacitySlotOf` спрашивает компонент), поэтому
  пульсация со сдвигом фазы по клонам не выражается в принципе. Нужна альфа по индексу клона.
- **[P2] Композиторный канал для element-opacity.** Анимированная element-opacity тикает на loop, не на рендер-потоке.
  `Compositor.TryTakeOver` для Paint ждёт Brush-таргет.
- **[P2] `LayerOpacity` / offscreen-слой.** Групповая `Opacity` двоит альфу на пересечениях ДЕТЕЙ внутри поддерева:
  каждый ребёнок рисуется своей помноженной альфой, и на нахлёсте фона остаётся `(1−α)²` вместо `(1−α)`. Правильно —
  собрать поддерево в offscreen-слой при полной непрозрачности и положить слой один раз. Каскадом это не чинится в
  принципе. **С аналитическим сглаживанием больше НЕ связано:** самоперекрытия полупрозрачной обводки закрыты через
  максимум покрытия в глубине (`9937bbc`), без offscreen-цели. `OPACITY_MODEL_PLAN.md` §1 п.2.
- **[P3] `OpacityMask`** — вне скоупа.

## Рендер / GPU

- **[P2] Кисть на многоугольнике держится ТОЛЬКО на батчах.** Градиент, паттерн/шум и текстура рисуются на
  `RegularPolygon` через SDF-проходы (`GradientRectCollector`/`PatternRectCollector`/`TexRectCollector`, ветка формы
  2 в `BrushShapeDistance`). Но если батч ОТКАЖЕТ — повёрнутый или скошенный мир, переполнение буфера инстансов —
  фигура уходит на по-юнитный меш, а он такие кисти не красит: замер до появления батчей давал 82-178 закрашенных
  пикселей вместо 2752 (сплошная заливка того же гексагона). Сейчас не воспроизводится, потому что батчи забирают все
  эти случаи. У эллипса устройство отката такое же, но ЭТО НЕ ЗАМЕРЕНО. Чинить там же, где чинится по-юнитная
  заливка кистью, а не отдельным путём для многоугольника.

- **[P2] `Ellipse` рисуется внутри своей коробки не так, как встаёт.** Ползунок маковского тумблера (`Ellipse` 18×18,
  `Margin="2"`, в дорожке 38×22) стоял вплотную к левому краю в выключенном положении и заметно дальше от правого во
  включённом — при том, что менялось ТОЛЬКО `HorizontalAlignment`.
  **Измерено (`AlignedMarginTests`, UITests):** раскладка тут ни при чём. И `Border`, и `Ellipse` встают ровно на 2 от
  того края, к которому выравнены, и в простом `Grid`, и внутри скруглённого `Border`. Тесты остаются как сторож.
  **НЕ доказано:** что именно происходит при отрисовке. Видимый перекос ушёл после замены примитива на `Border` со
  скруглением в половину размера, но чем эллипс отличается — не выяснено (кандидат: `EllipseType` по умолчанию
  `Sector`, а не `EdgeToEdge`). Бьёт по всем, кто ставит `Ellipse` с выравниванием, а не только по тумблеру.

## Эффекты / шейдерный тулинг

- **[P3] `Profile = 5.1` в проходах не значит НИЧЕГО.** После выноса DXC компилятор один — Slang, и профиль никуда не
  передаётся: он доезжает только до `EffectData.Shader.Level`, который никто не читает. 96 объявлений в 21 файле
  вводят в заблуждение (в `FontEffect.fx` соседние проходы стоят с 5.1 и 6.6, как будто это на что-то влияет). Либо
  убрать из грамматики, либо начать честно передавать в Slang как целевой профиль.

- **[P1] Запись материала НЕЛЬЗЯ вырастить, пока есть проход дерева — механизм НЕИЗВЕСТЕН.** Тринадцатое поле
  `Vector4F` в `MaterialRectItem`/`MaterialRectData` (192 → 208 байт) само по себе безвредно, и проходы дерева сами по
  себе безвредны. Вместе — `ErrorDeviceLost` на первых секундах, детерминированно, на ЛЮБОЙ вкладке, без единого
  сообщения слоя валидации (то есть API не нарушается, отказ происходит на GPU). Замерено, разведено по одному:

  | поле | пишется | проходы дерева | тело `WoodSurface` | итог |
  |---|---|---|---|---|
  | нет | — | да | полное, с лаком | живо |
  | есть | нет | нет | — | живо |
  | есть | да | нет | — | живо |
  | есть | да | да | полное | мертво |
  | есть | да | да | без лака / без фаски / распил константой | мертво |
  | есть | да | да | один проход вместо двух | мертво |

  Проверено и ИСКЛЮЧЕНО: вес шейдера (урезали до состояния проще живого), ветвление по значению из памяти, чтение
  самого поля (проба с давно существующим полем валится так же), фаска, число проходов, кеш шейдеров (ключ — хеш
  байтов SPIR-V, старый блоб подгрузиться не может), несвежий инкрементальный блоб (`.fxh` заведены как
  `AdditionalTexts`), раскладка и шаг буферов (везде `Marshal.SizeOf`, сравнение зеркала побайтовое). В стеке
  падения фигурировал `ComputePushDataLayout`. Обход: код распила и лака увезли в свободную `Light.w`, запись
  осталась 192 байта. **Пока это не понято, любая правка, растящая запись материала, обязана проверяться живым
  запуском.**

- **[P2] Ужать входные записи вместо того, чтобы их растить.** Прямое следствие пункта выше: подход «уложиться в
  имеющийся размер» уже дважды провёл дальше, чем рост. Жир есть — `Stroke1` этот батч не использует вовсе, у `Clip`
  занята только `.x`, а `Tint`/`StrokeColor` и цветовые половины `Surface`/`Response` это цвета, которым хватило бы
  упакованного `uint` или `half4` (вдвое меньше). Под шестьдесят байт из 192.
  **Границы, которые нельзя переходить:** `Bounds` — координаты, у `half` целые точны лишь до 2048, дальше геометрия
  задрожит; `Params` — там НОМЕРА СЛОТОВ таблицы преобразований и непрозрачности, слипание номеров даст чтение чужого
  узла, то есть тот же отказ, только тихо и на большом дереве. `half` в storage-буфере требует `shaderFloat16` и
  16-битного доступа, в C# понадобится своя `Vector4H`. И обязательное условие: сегодня стороны совпадают
  ТРИВИАЛЬНО (всё `float4`), а со скалярами раскладки C# и std430 считаются по разным правилам — ужимать только
  вместе с тестом, сверяющим `Marshal.SizeOf` с размером, который заявляет шейдер, чтобы рассогласование падало на
  сборке, а не на драйвере.

- **[P3] Дерево на МЕШЕВЫХ фигурах — один распил.** У звезды, многоугольника и произвольного контура запись —
  `PatternGeomData`, где четвёртая компонента света занята слотом скруглённой обрезки, а свободных чисел нет. Поэтому
  `MaterialWoodMeshPS` прибит к «плоский распил, лакировано», что бы ни стояло в кисти. Развязывается тем же, чем
  пункт выше: освободить место ужатием, а не ростом.

- **[P3] `MaterialBrush.Anisotropy` не читается НИЧЕМ.** Растяжение блика вдоль волокна убрали из металла (под
  фиксированной ортопроекцией у длинной оси нет разброса углов, чтобы себя показать), у бархата оно и не читалось, а
  на мешевом носителе доехать не могло: там его компонента — слот обрезки. Свойство осталось на кисти и молча ничего
  не делает. Либо честно применить в sheen-доле, либо убрать.

## Раскладка

- **[P2] Полоса вкладок не виртуализована.** `TabControl` строит все вкладки сразу: 300 вкладок подвешивают старт. Не сводится к «включить `VirtualizingPanel`»: ширина вкладки неравномерная (а виртуализация `StackPanel` построена на равномерной ячейке), закреплённые живут в отдельном НЕвиртуализуемом хосте, и нужны ответы на «где выбранная» (прокрутка, индикатор) и «куда встаёт при перетаскивании». Начинать с `TryGetItemRect`, как для строк списка. Ловушка: контейнеры раздаёт сам `TabControl` (`ContainerOfTab` спрашивает свой генератор первым) — при виртуализации контейнера может не быть, и все, кто спрашивает «где вкладка», обязаны это пережить.

## Анимация / композитор

- **[P2] `DoubleAnimation` (`RunningAnimation`) не композитится** — только keyframe `Animation`. Лечение то же: pure curve + канал.
- **[P3] Gradient-stop sweeps (shimmer) не композитятся** — таргет `GradientStop`, не `Brush`. Остаётся на loop.
- **[P3] `Compositor.RefreshBases()`** — раз в кадр на энтри (lock + property read). Пересмотреть, если композитных анимаций станет много.

## Платформенный слой / потоки

- **[P2] Обои рабочего стола читаются только под Windows.** `IDesktopWallpaperPlatform` реализует один
  `WindowsDesktopWallpaper`; на macOS и Linux слюда падает на видимый откат (тонирование цвета фона). Обои там
  доступны штатно — нужны реализации. `PlatformSettings.VirtualScreen` тоже пока только виндовый, а без него
  десктопный якорь ведёт себя как оконный. На Wayland глобальных координат окна нет в принципе — там десктопный
  якорь неосуществим, и это не наша недоделка. Своя картинка (`MaterialBrush.Source`) не зависит ни от чего из
  этого и работает везде.
- **[P3] Хост без своего `Main`** (тест-раннер, плагин в чужом приложении — `[STAThread]` поставить некуда): нужен отдельный опт-ин `RunOnDedicatedThread()` только под Windows, не трогая дефолтный путь. Ловушка: перегрузка `UIApplication.Run(IWindow)` — окно, собранное вызывающим до `Run`, создаст HWND на чужом потоке.

## Ввод / фокус

- **[P3] Стойка адорнера в МИРОВЫХ единицах.** `Adorner.ClipStandoff` расширяет клип вьюпорта в мировых единицах, поэтому под масштабирующим предком (DPI, ZoomBox) допуск приблизительный.
- **[P3] Фокус уходит из дерева, когда его строка уезжает за экран.** Пока строка не построена, фокус держит сам `TreeView` (клавиши работают, кольцо не рисуется) и возвращает его на строку, как только та реализована. Если фокус в этот момент был ВНЕ дерева, кольцо не встанет — воровать фокус нельзя. Обобщённого ответа «место клавиатуры в виртуализованном списке» для `ListBox` и `ItemsControl` нет, только для дерева.

## Риббон

- **[P2] Data-команды внутри группы не получают размер.** `RibbonGroup.ItemsSource` + `ItemTemplate` даёт `ContentPresenter`-контейнеры, а `RibbonGroupPanel` пишет `Ribbon.Size` в контейнер — до самой кнопки внутри шаблона он не доходит. Либо группа должна раздавать контейнеры-команды, либо размер обязан наследоваться. `docs/RIBBON_PLAN.md` §12.

## Строки / локализация

- **[P2] Интерфейсные строки живут ХАРДКОДОМ на месте использования.** Ни `.resx`, ни словаря, ни менеджера строк в
  движке нет. Пока их немного и почти все в теме (`RibbonQuickAccessMenuItem` — «Add to quick access» / «Remove from
  quick access», подсказки «Back», «Collapse the ribbon»), но тема — не словарь, а строка контрола обязана быть
  переводимой. Нужен словарь с подстановкой по ключу, чтобы тема ссылалась на ключ, а не несла текст. Заводить ДО того,
  как строки расползутся по десяткам файлов.

## Дизайн / будущее (не стартовало)

- **[P3] Обводки текста НЕТ.** Проход, который её изображал, был недостижим и снесён. Два маршрута, различаются не
  качеством, а потолком ширины: **из поля** (полоса вокруг контура 0.5) — API это ширина и цвет, стыка там не бывает
  (обводка из SDF есть евклидово смещение, круглый стык получается по построению; митра/фаска требуют смены метрики,
  а положение углов глифа в шейдере неизвестно), потолок ~±8 текселей при `pixelRange = 16`; **из геометрии** (контуры
  глифа через тот же расширитель обводки, что и у фигур — так это делает D2D) — любая ширина и настоящий выбор стыка
  ценой тесселяции.
- **[P3] Pointer / multi-touch** — абстракция Pointer над mouse-only вводом.
- **[P3] Adamantium.Fonts** — пробелы стека: BiDi / line-break / fallback / hinting.
- **[P3] Vision** — Unity/Unreal-уровень IDE + UI внутри 3D. `engine-vision-positioning`.
