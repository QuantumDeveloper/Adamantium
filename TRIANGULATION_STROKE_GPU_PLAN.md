## 0. Кратко (TL;DR)

- **Режимы мисномерены — но ЗЕРКАЛЬНО твоей памяти (проверено эмпирически, прогон триангулятора).** Реально:
  - **`EvenOdd` (имя) = настоящий even-odd.** Бублик → дырка (при любой намотке); перекрытие → пустое (чёт. пересечений); «бабочка» → оба крыла. Корректно. **Настоящий even-odd у тебя УЖЕ ЕСТЬ.**
  - **`NonZero` (имя) = по факту `OuterContour`** (залить внешнюю границу, выкинуть все внутренние контуры/дырки **независимо от намотки**). Бублик любой намотки → сплошной; перекрытие → объединение сплошное. Это **не** истинный non-zero (тот при противоположной намотке дырку бы оставил).
  - **`FillRule.OuterContour` (enum) — мёртв**, даёт результат идентичный `EvenOdd` (fallthrough).
  - Итог: твоё «EvenOdd по факту outer contour» — наоборот: outer-contour-поведение сидит под именем **`NonZero`** (и им рисуются обводки/`StrokeGeometry`). Истинного non-zero winding нет вовсе. §2 — таблица.
  - **Истинный non-zero НУЖЕН** (у тебя есть SVG-загрузчик; SVG по умолчанию `nonzero`, и текущее «NonZero»=OuterContour ломает дырки в буквах «O»/«A»/«8» и т.п.). → план: добавить настоящий non-zero, а текущее поведение `NonZero` переименовать в `OuterContour`. §3, §7.
- **⚠️ ПРОИЗВОДИТЕЛЬНОСТЬ — главная боль (замерено, Release).** Триангулятор **квадратичен по времени И по числу треугольников** на вогнутых контурах: выпуклый круг 2048 точек = **144 мс**; вогнутая «шестерёнка» 1024 точки = **6.7 СЕКУНДЫ** и **64 204 треугольника** (вместо ~1022!). Это и медленно, и грузит GPU слайвер-треугольниками. Причины: O(n²) скан самопересечений на каждом контуре + O(n²) raycasting + трапецоидная заливка даёт O(n²) треугольников. Лечится сменой ядра (earcut/монотонная декомпозиция → O(n log n), ~n−2 треугольника) + выпуклый fast-path + ленивый скан самопересечений. §2 «Производительность».
- **Ядро заливки одно — even-odd parity scanline** (`Triangulator.cs:147-156`, `x % 2 == 0`), без winding-логики. Режим меняет только то, какие сегменты доживают до ядра: `NonZero`-имя удаляет внутренние контуры → остаётся внешняя граница (= OuterContour), `EvenOdd`-имя ничего не удаляет → честная parity-заливка.
- **GPU-направление (по твоему решению): SDF НЕ делаем.** Вместо этого — **единая система рендеринга линий для абсолютно любых форм**. CPU генерит сырой контур (centerline формы) + общие параметры (`Pen`), отдаёт на GPU, а GPU формирует из контура линию с заданными параметрами. Один путь для line/rect/rounded-rect/ellipse/path/border. §6.
- **Новая первоклассная возможность линии** (нужна для твоего кастомного прогресс-бара): **trim / частичная отрисовка** — видимый участок `[start..end]` вдоль линии. Толщина у линии **постоянная** (переменной толщины НЕ нужно); прогресс-бар — это просто две линии одного контура с разной постоянной толщиной, у накладной `trim = 0..progress`. §4, §6.
- **Расхождение в бордерах (твоя заметка):** `Border` сейчас вообще не использует `Pen`/`StrokeGeometry` — заливает кольцо из двух `RectangleGeometry` через `CombinedGeometry.Exclude` (`Border.cs:94-116`), а Shape центрирует обводку `±thickness/2`. Это надо унифицировать вокруг явного **выравнивания обводки** (Inside/Center/Outside) и единой системы линий. §5.

## 1. Карта архитектуры (поток данных)

```
Control.OnRender(IDrawingContext)
  → DrawRectangle / DrawGeometry / DrawLine / DrawEllipse  (кладёт DrawCommand + Payload)
      → подтип RenderUnit (RenderUnit.cs)
           ctor / UpdateWithDrawCommand:
             geometry.ProcessGeometry(GeometryType.Both)      // CPU-триангуляция ЗАЛИВКИ
                 → Geometry.Mesh (List<Vector3>, треугольники)
             ProcessStrokeData(pen, geometry)                 // CPU-ОБВОДКА (RenderUnit.cs:37)
                 → new StrokeGeometry(pen, geometry)          // StrokeGeometry.cs
                     по контурам: GenerateStroke()            // offset top/bottom + joins + caps
                        → список MeshContour → Polygon(NonZero).FillIndirect()
                        → Triangulator.Triangulate()          // ядро even-odd parity
                 → StrokeRenderComponent (заливает vtx/idx буфер)
  → GeometryRenderer / StrokeRenderer .Render()  → UIBasicEffect (только VS+PS, UIBasicEffect.fx)
```

**Узкое место для анимации:** `RequiresBufferRebuild` (по всему `RenderUnit.cs`) пере-запускает `ProcessGeometry` + `ProcessStrokeData` и пересобирает GPU-буферы при любом изменении геометрии **или** пера. Анимация толщины/радиуса/размера/точек/прогресса = **полная CPU-ретриангуляция + перезалив буферов каждый кадр**. Это и уносим на GPU.

**Где формируется контур (источник истины — на CPU, как ты сказал):** каждая фигура уже умеет отдавать контур(ы) (`RectangleGeometry`, `EllipseGeometry`, `LineGeometry`, `PathGeometry`, `StreamGeometry`, `GeometryGroup`, `Shapes.Polygon`). Эти сырые контуры и пойдут на GPU.

## 2. Триангулятор — разбор и вердикт по режимам

### Что делает ядро (`Triangulator.cs`)
1. Сортирует точки по Y; горизонтальный луч на каждом уникальном Y (`:62-107`).
2. Для каждого луча — пересечение со **всеми** `MergedSegments`, сортировка по X.
3. Между соседними лучами строит «стенки» из реальных рёбер (`ConnectedSegments`, `:127-143`).
4. **Заливает между стенками `(0,1),(2,3),…` при `x % 2 == 0`** (`:147-156`). `CreateTriangles` (`:221-237`) — лишь гигиена порядка вершин.

➡️ Это чистый **even-odd parity scanline fill**, без знакового winding.

### Эмпирическая таблица истинности (прогон триангулятора, точка = «залита/нет»)
| Фигура | `EvenOdd` (имя) | `NonZero` (имя) | `OuterContour` (enum) |
|---|---|---|---|
| Бублик, одинак. намотка | дырка (центр пуст) | **сплошной** (дырка залита) | дырка |
| Бублик, против. намотка | дырка | **сплошной** | дырка |
| 2 перекрыт. квадрата, одинак. | перекрытие пусто | объединение сплошное | перекрытие пусто |
| 2 перекрыт. квадрата, против. | перекрытие пусто | объединение сплошное | перекрытие пусто |
| «Бабочка» (самопересеч.) | оба крыла | оба крыла | оба крыла |

➡️ **`OuterContour` (enum) ≡ `EvenOdd` побитово** (мёртв, fallthrough).

> ⚠️ Не путать два смысла слова «OuterContour»: **поведение** outer-contour (выкинуть дырки, залить внешнюю границу) реально существует, но привязано к ветке `if (FillRule == NonZero)` — то есть лежит под **именем `NonZero`**. А enum-**значение** `OuterContour` не упомянуто ни в одной ветке → идёт по дефолтному пути → даёт even-odd. Поэтому: нужное поведение есть (под `NonZero`), а имя `OuterContour` — мёртвое. Переименование `NonZero`→`OuterContour` сводит имя к поведению.

### Вердикт (по фактам, а не по памяти)
- **`EvenOdd` (имя) — это НАСТОЯЩИЙ even-odd.** Дырки появляются, перекрытия выдалбливаются независимо от намотки. Работает корректно. **Настоящий even-odd у тебя уже есть.**
- **`NonZero` (имя) — это по факту `OuterContour`:** удаляет все внутренние контуры и заливает внешнюю границу сплошняком, **независимо от намотки**. Это НЕ истинный non-zero (тот при противоположной намотке оставил бы дырку). Именно этим режимом рисуются обводки (`StrokeGeometry` → `Polygon(NonZero)`), и для обводок такое поведение как раз правильное (контур обводки должен заливаться сплошным).
- **Истинного non-zero winding в коде нет вовсе.**
- Значит твоя память зеркальна: outer-contour-поведение сидит под именем `NonZero`, а `EvenOdd` — честный even-odd.

### План по триангулятору (с учётом фактов)
1. **Зафиксировать поведение тестами** (та самая таблица выше → ассертящие тесты) — до правок, т.к. это же ядро триангулирует глифы шрифтов и пути (`TextLayout`, CFF-парсер, `PathGeometry`/`StreamGeometry`).
2. **Переименовать `NonZero` → `OuterContour`** в точках использования (`StrokeGeometry.cs:108`, `CombinedGeometry.cs:254,277`, icon-templates `PointLightIconTemplate`/`CameraIconTemplate`, тесты). `EvenOdd` оставить как есть (он корректен). Сделать enum источником истины, удалить мёртвый дубль-смысл.
3. **Истинный non-zero — ДОБАВИТЬ** (нужен для SVG, см. §8). Чистый дизайн: считать вклад winding прямо в scanline и заливать по `mode switch { EvenOdd → count&1, NonZero → winding!=0, OuterContour → внешняя граница }` — одно ядро, три честных режима, машинерия удаления внутренних в `MergeContours` уходит.

### Производительность (ЗАМЕРЕНО, Release, медиана)

| Вход | n | треуг. | время |
|---|---|---|---|
| Круг (выпуклый) | 64 | 62 | 1.0 мс |
| Круг | 256 | 254 | 4.2 мс |
| Круг | 1024 | 1022 | 34 мс |
| Круг | 2048 | 2044 | **144 мс** |
| Шестерёнка (вогн.) | 128 | 1 000 | 4.5 мс |
| Шестерёнка | 256 | 4 000 | 43 мс |
| Шестерёнка | 512 | 16 036 | 454 мс |
| Шестерёнка | 1024 | **64 204** | **6.7 с** |
| 256 отд. квадратов | — | 512 | 1.7 мс |

**Выводы:**
- **Время ~O(n²)**: на круге удвоение n → ×4.2 времени. 144 мс на выпуклый 2048-угольник — это очень много (выпуклый случай вообще должен быть мгновенным «веером» за O(n)).
- **Хуже того — число треугольников ~O(n²) на вогнутых формах**: 1024-вершинная шестерёнка даёт **64 204** треугольника вместо ~1022. Трапецоидная заливка плодит слайвер-треугольники (на каждом скан-лайне × число пролётов). Это бьёт дважды: медленно на CPU + лишние вершины на GPU.
- Путь контейнеров (много отдельных контуров) — дёшев; квадратичность сидит **внутри одного контура**.

**Причины (из кода):**
- `MeshContour.RemoveSelfIntersections` `:174` — O(сегменты²) скан «все против всех», запускается **на каждом** контуре, даже выпуклом без пересечений (для n=2048 ≈ 4 млн тестов).
- `Triangulator.Triangulate` — луч на каждом уникальном Y (n) × пересечение со всеми сегментами (n) = O(n²); плюс вложенный цикл `startEndSegments` O(upper×lower) на каждую полосу.
- Трапецоидная заливка `(0,1),(2,3)…` на каждой полосе → O(пролёты×полосы) треугольников.

**Что делать (отдельный трек, важно):**
1. **Выпуклый fast-path:** дешёвая проверка выпуклости → триангуляция «веером» за O(n), n−2 треугольника. Круг/эллипс/rounded-rect = выпуклые → мгновенно.
2. **Сменить ядро на earcut (РЕШЕНО)** — порт mapbox earcut на C# (почти линеен на практике, n−2 треугольника, дырки через «мостики»; устойчив к грязному входу — важно для SVG/шрифтов). Монотонная декомпозиция (O(n log n) гарант.) отложена — сложнее и хрупка к вырождениям, переходить только если упрёмся в патологический O(n²) earcut. **Важно:** earcut триангулирует уже готовую область → нужен явный **пред-шаг «fill-rule resolution»** (определить внешние контуры/дырки по `EvenOdd`/`NonZero`/`OuterContour`, при необходимости разрешить самопересечения), затем earcut.
3. **Ленивый скан самопересечений:** не гонять O(n²) на каждом контуре. Заведомо простые (выпуклые, примитивы движка — флаг `IsKnownSimple`) — пропускать совсем; «недоверенные» (SVG/пользовательские пути) — sweep-line (Bentley–Ottmann) O((n+k)·log n).
4. **Не пересэмплировать кривые** в тысячи точек, если можно меньше; для curve-форм держать adaptive flattening.

**Ожидаемый выигрыш (теория, от замеренной базы):**
- Сложность на контур: выпуклые/простые O(n²) → **O(n)**; вогнутые чистые O(n²)-время + O(n²)-треуг. → **~O(n)-время + (n−2) треуг.** (earcut); грязные (SVG) O(n²) → **O((n+k)·log n)** на разрешение + O(n) earcut.
- Масштабирование: сейчас удвоение n → ×4 по времени; после → ×2. Чем сложнее форма, тем больше разрыв.
- Проекция от замеров (оценочно): круг 2048: 144 мс → **~0.1 мс** (веер), ~1000×. Шестерёнка 1024: 6.7 с/64 204 треуг. → **~0.5 мс / ~1022 треуг.**, т.е. **тысячи× по времени и ~60× по числу треугольников**. Сокращение треугольников — двойная выгода: меньше работы CPU и меньше вершин на GPU.
- Где выигрыша почти нет: мелкие формы (rect = 4 вершины) и так мгновенны. Весь выигрыш концентрируется на кривых высокой тесселяции, глифах, SVG, сложных путях.

|---|---|---|---|
| 64 | 1.04 мс | 0.089 мс | ~12× |
| 512 | 8.1 мс | 0.69 мс | ~12× |
| 1024 | 34 мс | 1.75 мс | ~19× |
| 2048 | 144 мс | **4.45 мс** | **~32×** |

Масштабирование стало **линейным** (удвоение n → ×2.0–2.5 вместо ×4.2). До проектных ~0.1 мс не дошли (остаток — аллокации в `Copy()`/`SplitOnSegments`, нужны только для `ProcessedContours`/outline; можно срезать позже). Вогнутая шестерёнка не изменилась (ждёт earcut P2). **0 регрессий**, +3 новых теста (IsConvex / truth-table / convex-fan). Файлы: `MathHelper.cs`, `Triangulator.FanTriangulate`, `Polygon.FillIndirect`; тесты `FillRuleAndConvexTests.cs`, бенч `TriangulatorBenchmark.cs` (Category=Benchmark).

**P2a РЕАЛИЗОВАНО (earcut для одиночных контуров) — ЗАМЕРЕНО (Release):** порт mapbox earcut (`Earcut.cs`) + `Triangulator.EarcutTriangulate`. Простые (несамопересекающиеся) одиночные контуры → earcut (`TriangulateContour`); самопересекающиеся (флаг `MeshContour.HadSelfIntersections`) остаются на scanline (там even-odd разрешает пересечения). Вогнутая шестерёнка:

| n | было (scanline) | стало (earcut) | выигрыш |
|---|---|---|---|
| 256 | 43 мс / 4000 треуг. | 7.8 мс / **254** | ~5.5× / 16× треуг. |
| 512 | 454 мс / 16036 | 7.6 мс / **510** | ~60× / 31× треуг. |
| 1024 | **6711 мс / 64204** | **21.5 мс / 1022** | **~312× / ~63× треуг.** |

Треугольников теперь **n−2** (без слайверов). **0 регрессий, +1 тест** (concave-earcut). Файлы: `Earcut.cs`, `Triangulator.EarcutTriangulate`, `MeshContour.HadSelfIntersections`, `Polygon.TriangulateContour`.

**P3 РЕАЛИЗОВАНО (broad-phase скан самопересечений) — ЗАМЕРЕНО:** O(n²) all-pairs в `MeshContour.RemoveSelfIntersections` заменён на X-sweep (сортировка по min-X + active-list; результат идентичен — X-непересекающиеся сегменты не могут скреститься). Шестерёнка 1024: **21.5 → 10.6 мс** (медиана; min ~7 мс). **0 регрессий.** Суммарно по шестерёнке 1024: **6711 → 10.6 мс (~630×)**.

**P2b РЕАЛИЗОВАНО (earcut с дырками) — ЗАМЕРЕНО:** после `MergeContours` (он уже применил fill-rule) survivors берутся как кольца с **gate по степени вершин = 2** (чистая вложенность; пересечения/T-стыки → fallback на scanline). Кольца реконструируются обходом, вкладываются по point-in-polygon, earcut'ятся с дырками (`Triangulator.EarcutWithHoles`). Even-odd nesting survivors корректен для ЛЮБОГО fill-rule (merge уже разрулил). Бублик: even-odd → дырка/**8 треуг.**, nonzero → solid/**2 треуг.** (раньше scanline + слайверы). **0 регрессий, +2 теста.** Файлы: `Triangulator.EarcutWithHoles`, `Polygon.TryTriangulateWithHoles`/`PointInPolygon`.

> ⚠️ **НОВОЕ узкое место (обнажено P2b): `MergeContours` сам по себе O(n²).** Annulus (кольцо outer+inner): n/кольцо=256 → 48 мс; 1024 → **1006 мс**, при этом треугольников верно 2n. Триангуляция (мой код + earcut) тут O(n); тормозит `ProcessContoursIntersections` (outer×inner пересечения) + `MarkSegments` (луч на сегмент) — оба O(n²). Это **пред-существующее** (старый scanline-путь тоже звал MergeContours), P2b лишь убрал поверх него O(n²)-scanline и слайверы. **→ P4:** broad-phase/sweep-line для inter-contour пересечений и маркировки (аналог P3, но для merge). Срежет multi-contour до ~O(n log n).

**P4 РЕАЛИЗОВАНО (обход O(n²)-merge) — ЗАМЕРЕНО:** вместо ускорения merge — **единый pre-pipeline fast-path** `Polygon.TryFastTriangulate`, заменивший разрозненные P1/P2a/P2b-хуки. Алгоритм: собрать все закрытые контуры → broad-phase скан пересечений `HasProperIntersections` (X-sweep, ~O(n log n)) → если чисто (только вложенность): вложенность по point-in-polygon + fill-rule (EvenOdd/OuterContour: чёт.глубина = заливка, нечёт.внутри = дырки; NonZero: только глубина-0 solid) → earcut (одиночный выпуклый → веер short-circuit). Пересечения/самопересечения → полный pipeline (merge+scanline). Это **обходит и O(n²)-скан, и O(n²)-merge** для чистых случаев (rect/ellipse/глифы/бублики/SVG-с-дырками).

| Кейс | до P4 | после P4 | выигрыш |
|---|---|---|---|
| Annulus 1024/кольцо (дырка) | 1006 мс | **~18 мс** | **~57×** |
| Шестерёнка 1024 (вогн.) | 10.6 мс | ~10 мс | (≈, broad-phase вместо скана) |
| Круг 2048 (выпукл.) | — | веер (short-circuit) | без регресса |

**0 регрессий.** Старый `TryTriangulateWithHoles` (post-merge) убран как избыточный. Fallback-путь (реально пересекающиеся/самопересекающиеся контуры) остаётся на merge+scanline (с P3-broad-phase в скане).

**ИТОГ по перфу триангулятора:** все чистые случаи (выпуклые/вогнутые/вложенные-с-дырками) → ~O(n)/O(n log n); только реально пересекающаяся/overlapping геометрия (редко) остаётся на O(n²)-fallback (корректно). Шестерёнка 1024: **6711 → ~10 мс**; annulus 1024: **1006 → ~18 мс**.

**Тесты приведены в соответствие реальности:** 4 хрупких golden (ComplexPolygon/DoubleStar ×2, точные числа) заменены на coverage-тесты (`TriangulationTests` — star/bowtie инварианты); `Concave2Test` и `PolygonHas[No]SelfIntersections` починены (падали из-за вызова `RemoveSelfIntersections` без `SplitOnSegments`, а не из-за бага); `FillRuleAndConvexTests` — основное coverage-покрытие. **Все триангуляционные тесты зелёные (75 прошло).**

> ⚠️ **Осталось 3 пред-существующих падения, НЕ связанных с триангуляцией** (были до этой работы): `RayIntersectsLineSegment2D_Correct` (Collision2D — луч ↔ конец отрезка) и `Opposite`/`Zero` (NearlyEqual — сравнение float/double). Это баги/устаревшие тесты в ДРУГИХ фичах; трогать `Collision2D` рискованно (его использует и триангулятор). Разбирать отдельно.

## 3. Режимы fill-rule — итог

- **`EvenOdd` (имя)** = настоящий even-odd. Корректен, оставляем. Используется для заливок Path/Stream/GeometryGroup/Shapes.Polygon.
- **`NonZero` (имя)** = по факту **OuterContour** (внешняя граница, дырки выкинуты, намотка игнорируется). Используется для обводок. → переименовать в `OuterContour`.
- **`OuterContour` (enum)** = мёртв (≡ EvenOdd). → станет настоящим именем для поведения, что сейчас под `NonZero`.
- **Истинный non-zero winding** — отсутствует, **НУЖНО ДОБАВИТЬ** (SVG-загрузчик: `fill-rule="nonzero"` — дефолт SVG; сейчас он маппится на OuterContour и ломает дырки). SVG-маппинг после правок: `nonzero`→настоящий `NonZero`, `evenodd`→`EvenOdd`.

## 4. Обводка — разбор и целевые возможности

`StrokeGeometry.cs` (CPU): по сегментам смещает top/bottom на `±thickness/2` вдоль нормали → **центрированная обводка** (`:671-678`); стыки `Bevel/Miter/Round` (`:784-816`); окончания `Flat/Square/ConvexTriangle/ConcaveTriangle/ConvexRound/ConcaveRound` (`PenLineCap.cs`, Concave/Convex — твои нестандартные); пунктиры (`SplitGeometryToDashes`). Каждый сегмент/стык/окончание триангулируется отдельным `Polygon(NonZero)` — много мелких контуров на кадр.

### Целевые возможности единой системы линий
- **Любая форма как контур.** line/rect/rounded-rect/ellipse/path/polygon/border сводятся к контуру(ам) — единый вход. Различается только форма контура, параметры общие.
- **Постоянная толщина** (переменной толщины НЕ нужно). Толщина задаётся одним числом на линию.
- **Trim / частичная отрисовка** — видимый участок `[trimStart..trimEnd]` вдоль линии. Накладная линия идёт от 0 до `progress`. _Решено:_ внутри — нормированный `[0..1]`, плюс метрический (px) API, конвертящийся через полную длину дуги (CPU).
- **Выравнивание обводки** `StrokeAlignment { Center, Inside, Outside }`. _Решено:_ дефолты — `Shape` → `Center` (как WPF), `Border` → `Inside`.
- `PenLineJoin.MiterClip` + `MiterLimit` (сейчас нет — острый miter ничем не ограничен).
- _Решено:_ всё перечисленное (`trim`/`alignment`/`miterLimit`) кладём в класс **`Pen`**, отдельный `StrokeStyle` не вводим.

### Кастомный прогресс-бар (твой кейс) на этой системе
- Базовая линия: контур `C`, постоянная **тонкая** толщина (1–2 px), `trim = 0..1` (вся длина).
- Накладная линия: тот же контур `C`, постоянная **толстая** толщина (3–4 px), `trim = 0..progress`.
- В кадре одновременно видны тонкий «хвост» и толстый «пройденный» участок, пока толстая часть не дойдёт до конца — как в обычном прогресс-баре, но по линии любой формы.
- Анимируется **только параметр `progress`** (trim накладной линии) — без CPU-перестроения геометрии. Годится для игр/стилизованных загрузок.

## 5. Border + выравнивание (твоя заметка)

- `Border` **не использует `Pen`/`StrokeGeometry`**: строит `outer`/`inner` `RectangleGeometry` и заливает `CombinedGeometry.Exclude` (`Border.cs:94-116`); `Measure/Arrange` урезают на `BorderThickness/2` (`:59,72`). Shape урезает на `StrokeThickness/2` (`Shape.cs:135`). Две несогласованные модели, и ни одна не = WPF «центрирование по внешнему краю».
- **План:** ввести явный `StrokeAlignment`; пересчитать `Measure/Arrange` под него (Center → резерв `thickness/2`; Inside → `thickness` внутрь, контент = bounds − thickness; Outside → `thickness` наружу = твоё текущее «строго наружу»). Переписать `Border` как обычный stroked rounded-rect (контур `RectangleGeometry` + общая система линий) — тогда выравнивание/радиус/толщина приходят из одного пути с шейпами.

## 6. Единая GPU-система линий (без SDF)

**Принцип (по твоему решению):** источник истины — обводка на контроле. CPU генерит **сырой контур** (centerline формы) + блок параметров; передаёт на GPU; GPU **формирует линию** (расширяет контур в треугольники) с заданными параметрами. Никакого SDF и никаких спец-кейсов по форме — форма различается только контуром.

### Поток
```
CPU:  фигура → контур(ы) {точки[], closed} + StrokeParams
        StrokeParams = { thickness, join, cap(start/end), miterLimit,
                         alignment, dash, trim(start/end), brush/color }
      → загрузка контура + StrokeParams в storage-буфер (по адресу, BDA уже есть)
GPU (compute):  читает контур+параметры
      → считает длину дуги по вершинам (префикс-суммы)
      → расширяет сегменты в квады; стыки miter/bevel/miter-clip/round; caps
      → применяет trim[start..end], alignment (толщина постоянная)
      → пишет vertex buffer + аргументы VkDrawIndirect
GPU (draw):  обычный triangle-list через UIBasicEffect
```

### Почему compute, а не GS
- Round-стыки/окончания и переменная толщина → **переменное число вершин** на сегмент: GS упирается в `maxvertexcount`, compute — нет.
- Обходит NVVM-баг GS `OpFDiv` на Turing (память `geometry-shader-fdiv-nvvm-bug`).
- Ложится на уже сделанные BDA/дескрипторы (кормить буферы по адресу).

### Важное следствие
- **Триангулятор перестаёт участвовать в обводках** — compute сам выдаёт треугольники. Триангулятор остаётся только для **заливок** (интерьеров). Это и упрощение, и большой выигрыш по перфу.
- CPU-`StrokeGeometry` оставить как fallback/референс для сравнения и для статики на первых порах.

### Сглаживание
- Уже включён MSAA X4 — на старте опираемся на него (не вводим вторичное AA, чтобы не задваивать края).

## 8. Риски и открытые вопросы

**Риски**
- NVVM GS `OpFDiv` AV на Turing → идём через **compute** (не GS); память `geometry-shader-fdiv-nvvm-bug`.
- Оговорки descriptor-heap на Turing → использовать рабочий маршрут descriptor_buffer/BDA; память `descriptor-heap-driver-limitation`.
- Рефакторинг/переименование режимов рискует регрессиями в заливке шрифтов/путей (то же ядро). Сначала тесты (Фаза 0).
- Точность длины дуги/стыков на острых углах и замкнутых контурах в compute — нужен референс CPU для пиксельного сравнения.

**Решено (зафиксировано):**
- **Истинный non-zero — НУЖЕН** (есть SVG-загрузчик, `nonzero` — дефолт SVG). → добавляем настоящий non-zero winding; текущее `NonZero`-поведение переименовываем в `OuterContour`; `EvenOdd` не трогаем. Итог — три честных режима `{EvenOdd, NonZero, OuterContour}`.
- **Trim** — поддержать оба способа: внутреннее представление одно (нормированное `[0..1]`), плюс метрический API (в px), который конвертится в нормированное через полную длину дуги (считается на CPU при генерации контура). Шейдер работает только с нормированным.
- **Параметры на `Pen`** — `trim`/`alignment`/`miterLimit` добавляем прямо в класс `Pen` (он уже держит caps/join/dash; его `Equals`/`GetHashCode` рулят `RequiresBufferRebuild`). Отдельный `StrokeStyle` не вводим.
- **Дефолтное выравнивание** — `Shape` → `Center` (как WPF), `Border` → `Inside`. От этого считается резерв места в `Measure/Arrange`.

**Открытых вопросов нет** — все решены. Дополнительно всплыло (см. §2 «Производительность»): триангулятор квадратичен по времени и по числу треугольников — это отдельный важный трек (Фаза 0.5).
```
